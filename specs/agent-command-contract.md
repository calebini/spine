# Spine Agent Command Contract

Status: Draft v0.4.1; executable low-level scheduling family implemented; atomic `schedule.create` specified but not implemented
Scope: Agent-facing command/request contract for authoring and inspecting Spine coordination truth
Created: 2026-06-19

## 1. Purpose

This document defines the first agent-operable Spine command contract. It lets local agents create, inspect, update, cancel, archive, relate, and prepare reminders for Spine items through stable request and response handlers without ad hoc SQL or embedded ledger calls in prompts.

The command contract is the public behavior core over Spine canonical ledger and services APIs. It inherits ledger validation, versioning, hashing, audit, timestamp, relation, work, and side-effect safety rules. It is not a separate coordination authority.

The CLI is the first expected transport adapter. Future MCP and localhost HTTP adapters call the same handlers and preserve the same request, response, and error semantics.

## 2. Authority

This contract depends on `specs/overview.md`, `specs/architecture.md`, `specs/ontology.md`, `specs/recurrence.md`, `specs/notifications.md`, `specs/schedule-create.md`, and `specs/SPINE_SPEC_VERSIONING_AND_FREEZE_POLICY.md`. If this document conflicts with `specs/ontology.md`, the ontology wins for ledger truth and this document must be corrected.

Spine is the canonical coordination ledger and planning fabric. External tools are projections or side-effect targets. The authoring commands in this contract do not send externally.

## 3. Command Core Shape

The stable command core lives behind the importable Python handler signature `spine.commands.handle(command: str, request: Mapping, context: CommandContext) -> Mapping`. The canonical command identifier is the dotted `resource.verb` value. Currently implemented contract command identifiers are `system.info`, `subject.upsert`, `subject_group.upsert`, `delivery_target.upsert`, `item.show`, `item.list`, `item.occurrences`, `item.archive`, `event.create`, `event.update`, `event.reschedule`, `event.cancel`, `task.create`, `task.update`, `task.complete`, `task.cancel`, `relation.create`, `relation.list`, `reminder.create`, `reminder.edit`, `reminder.disable`, `notification.opportunities`, `notification_work.materialize`, `recurrence.instance.add`, `recurrence.instance.remove`, `recurrence.instance.override`, `recurrence.series.edit`, and `occurrence_provenance.regenerate`.

`schedule.create` is the specified composite authoring identifier governed by `specs/schedule-create.md`. It is reserved but not implemented in the current runtime. Until its runtime, version declaration, fixtures, and behavioral tests land atomically, it is excluded from the implemented command set and `system.info.implemented_contract_versions`; invocation follows the normal `unsupported_command` result. Contract-only schemas and structural fixtures MUST NOT be interpreted as an implementation declaration.

CLI invocations such as `spine event create` are transport aliases. MCP tools and localhost HTTP routes may use local names, but each request and response maps to exactly one canonical command and returns that command in the `command` field.

`CommandContext` contains the ledger connection or path, `dry_run` boolean defaulting to `false`, transport metadata, optional `correlation_id`, optional runtime adapter bindings, and the future normalized `delivery_target_defaults` mapping defined by `specs/schedule-create.md`. A delivery-target default maps a request key to an existing canonical delivery-target ID; it is not adapter configuration, route creation, approval, or permission to send. Command authoring and bounded scheduling reads require only the ledger and explicitly declared normalized context; they never invoke an external adapter. Runtime workers resolve configured bindings only after durable work exists and the pre-write attempt gate succeeds. The command core does not depend on argparse, FastAPI, MCP server APIs, or another transport framework.

An unsupported canonical command identifier is a deterministic request failure and never mutates canonical rows. If the supplied identifier is syntactically dotted but not one of the MVP command identifiers, the command core returns `ok=false`, echoes that identifier in `command`, and reports `error.code=unsupported_command`, `error.field=command`. If a transport cannot resolve an invocation to a syntactically valid canonical command identifier, it returns `ok=false` without a `command` field and reports `error.code=unsupported_command`, `error.field=command`. The CLI maps both cases to exit `2` when transport control is recovered.

## 4. Common Request, Output, and Error Rules

Write commands require `command_id`, explicit `actor_subject_id`, and explicit UTC timestamps in `YYYY-MM-DDTHH:MM:SSZ` format. Except for the first-subject bootstrap rule, `actor_subject_id` must resolve before mutation. Unresolved actors fail with `referenced_row_not_found`, `field=actor_subject_id`, and CLI exit `4`.

Every command validates its request object against that command required and optional top-level field set before mutation. Unknown top-level request keys fail with `ok=false`, `error.code=unsupported_field`, `error.field=<key>`, and CLI exit `2`, unless the command explicitly names an extension map or transport metadata location that may contain additional keys.

Temporal-anchor output objects expose persisted anchor facts by value, not only IDs. Every temporal-anchor output includes `anchor_id`, `anchor_kind`, `created_at_utc`, and exactly the stored semantic fields for that kind: `utc_instant` for `instant_utc`; `local_date`, `local_time`, `timezone`, and `timezone_database_version` for `local_instant`; `local_date`, `timezone`, and `timezone_database_version` for `local_date`; `window_start_utc` and `window_end_utc` for `utc_window`; and `local_date`, `timezone`, and `timezone_database_version` for `local_window`. Optional source fields are returned only when stored. Missing referenced anchors in an otherwise valid item read fail closed with `ok=false`, `command=item.show`, `error.code=referenced_row_not_found`, and CLI exit `4`; `error.field` is the stored anchor ID field responsible for the failed read, such as `start_anchor_id`, `end_anchor_id`, `due_anchor_id`, or `defer_until_anchor_id`.

The recurrence input contract is the structured `spine.recurrence-authoring.v1` object defined by `specs/recurrence.md` and `contracts/schemas/recurrence-authoring.schema.json`. Exactly `event.create.start_anchor.recurrence_set`, `event.reschedule.start_anchor.recurrence_set` when attaching recurrence to a non-recurring event, and `task.create.due_anchor.recurrence_set` may carry that object. Recurrence remains forbidden on every other anchor role. The recurrence `time_basis` must agree with `anchor_kind`: `local_date`, `local_instant`, or `instant_utc`. Generated ids, revision facts, statuses, exclusions, overrides, and lineage are never accepted on initial authoring.

For item create commands, `coordination_items.created_at_utc` and `coordination_items.updated_at_utc` are both set to the command `created_at_utc`. Every successful version-creating item mutation advances the item shell `updated_at_utc` to that command action timestamp: `event.update` and `task.update` use `updated_at_utc`; `event.reschedule` uses `rescheduled_at_utc`; `event.cancel` and `task.cancel` use `cancelled_at_utc`; `task.complete` uses `completed_at_utc`; and `reminder.create` uses `created_at_utc`. Compatible same-command replay and validated no-op commands do not advance shell `updated_at_utc` because they create no new item version. `item.archive` follows its shell lifecycle rule and sets `updated_at_utc` to `archived_at_utc`.

Every command-created `coordination_item_versions` row uses the same action timestamp as its `created_at_utc` and the resolved `actor_subject_id` as `created_by_subject_id`, unless a command states a narrower rule. Create commands persist request `title`, optional `summary`, and optional `source_ref` into version 1. Create command `intent_hash` is computed from `title`, optional `summary`, and optional `source_ref`; `normalized_fields_hash` is computed from `title` and optional `summary` only. Absent optional fields are omitted from both hash payloads. Patch mutations persist resulting common item facts after applying the accepted patch, with `null` optional patch values represented as absent persisted optional fields. Lifecycle-only, reminder, and copied-detail mutations that do not change common item facts copy forward common facts and hashes from the target version.

Patch-bearing commands use one common field-level patch value contract. For `event.update`, `task.update`, and optional `event.reschedule.patch`, omitted patch fields leave the persisted fact unchanged. `title`, when supplied, must be a JSON string with at least one character; `null`, non-string values, and the empty string are invalid. `summary` and `source_ref`, when supplied, must be either a JSON string or `null`; a string persists that exact text value, and `null` clears the optional fact so it is absent from the new version and omitted from hash payloads. Non-whitelisted patch keys fail with `unsupported_field`, `field=patch.<key>`, and CLI exit `2`. Whitelisted fields with invalid values fail before mutation with `invalid_request`, `field=patch.<key>`, and CLI exit `2`. A patch object with no accepted semantic change after this normalization is a deterministic no-op under the command-specific no-op rules. `patch` itself must be an object when supplied; `null`, arrays, and scalar patch values fail with `invalid_request`, `field=patch`, and CLI exit `2`.

For canonical rows created directly by a write command, row IDs are deterministically derived from `command_id`, not randomness, ambient time, SQLite sequences, or transport state, unless an owning normative contract defines a more specific content-addressed preimage. Recurrence-generated identities use `specs/recurrence.md`; structured notification intent, policy, slot, opportunity, and materialized-work identities use `specs/notifications.md`. The sole caller-supplied MVP row-identity exception is `subjects.subject_id`: `subject.upsert` persists the caller-supplied stable subject identity and must not derive that `subject_id` from `command_id`. The MVP ID encoding for ordinary command-derived rows is `<prefix>_<sha256>` over Spine canonical JSON containing `derivation_version=spine.command-id.v1`, `command`, `command_id`, `row_role`, and `request_path`.

MVP write-command operation identity is the caller-supplied `command_id`, globally across canonical commands, not `(command, command_id)`. Every successful write outcome that consumes a `command_id` must create exactly one `command_receipts` row as the durable replay index for that `command_id`, including successful mutating branches, no-op branches, terminal lifecycle branches, and duplicate-safe `if_absent=true` reminder success. Command-created audit rows remain audit evidence and may duplicate replay facts in their payload hash input, but they are not the MVP replay index and are not used to discover cross-command `command_id` reuse. Before any fresh mutation or duplicate-safe success, a write handler must check `command_receipts` for the supplied `command_id`. If the receipt belongs to the same canonical command, the command-specific replay rules decide compatibility. If the receipt belongs to a different canonical command, the handler fails before mutation with `ok=false`, the requested command identifier, `error.code=semantic_conflict`, `error.field=command_id`, a stable message naming cross-command command ID reuse, and CLI exit `6`.

Registered ordinary command-derived row roles and prefixes are: `item` -> `item`, `audit` -> `audit`, `command_receipt` -> `command_receipt`, `relation` -> `relation`, `start_anchor` -> `anchor`, `end_anchor` -> `anchor`, `due_anchor` -> `anchor`, `defer_until_anchor` -> `anchor`, `location` -> `location`, `item_location` -> `item_location`, and `item_subject_role` -> `item_subject_role`. Recurrence, notification, provenance, and scheduled-work rows use the content-addressed registries in their owning specifications. A handler must not create a command-derived row for an unregistered `row_role`.

Produced-row identity uses stable request paths. Item shells use `/item`. Audit rows use `/audit` or `/audit/<effect>` when a command creates more than one audit row. Command receipts use `/`. Relations use `/relation`. Temporal anchors use their command field path. Initial supporting-set rows use array-indexed paths under `/locations` and `/subject_roles`. Notification rows use the content-addressed preimages in `specs/notifications.md`; audit and receipt rows still use this command-path registry. Copied version-scoped rows use `/copy_forward/<row_role>/<prior_id>` unless the owning structured contract defines successor identity. Composite artifacts whose identity is `(item_id, version)`, including item versions, event details, and task details, do not receive separate generated IDs.

Temporal-anchor inputs are objects with `anchor_kind` and the fields permitted by the ontology. `instant_utc` requires `utc_instant` and forbids local fields. `local_instant` requires `local_date`, `local_time`, `timezone`, and `timezone_database_version` and forbids `utc_instant`. `local_date` requires `local_date`, `timezone`, and `timezone_database_version` and forbids `utc_instant`. `utc_window` requires `window_start_utc` and `window_end_utc` with start less than or equal to end. `local_window` represents a full local-day window, requires `local_date`, `timezone`, and `timezone_database_version`, and forbids `local_time`, `utc_instant`, `window_start_utc`, and `window_end_utc`.

Every structured success response contains `ok=true`, `command`, and the command-specific stable identities and effect booleans. Every structured failure response contains `ok=false`, `command` when known, `error.code`, `error.message`, and `error.field` when a single request field or stored field is responsible. Common error codes are `invalid_request`, `unsupported_command`, `unsupported_field`, `missing_required_field`, `invalid_timestamp`, `referenced_row_not_found`, `wrong_item_type`, `stale_version`, `invalid_state_transition`, `semantic_conflict`, `environment_failure`, and `runtime_failure`.

CLI exit codes are normative: `0` success, `1` recovered unexpected runtime failure, `2` invalid request shape, unsupported commands, unsupported fields, missing required fields, invalid timestamps, invalid limits, wrong item type, and invalid lifecycle transitions, `3` CLI path/input/preflight failures, `4` unresolved references, `5` stale target versions, `6` semantic conflicts including incompatible replay and duplicate create without `if_absent`, and `7` environment failures such as a required OpenClaw binding missing for `channel=whatsapp`.

Deterministic ordering is part of output identity. Unless a command states a narrower order, user-visible lists order by stored canonical timestamp ascending, then stable ID ascending. `item.show` nested collections order locations by `role`, `item_locations.created_at_utc`, then `item_location_id`; subject roles by `role`, `item_subject_roles.created_at_utc`, then `item_subject_role_id`; notification policies by `notification_policies.created_at_utc`, then `policy_id`; and requested relations by the `relation.list` order. Outputs include truncation flags whenever a limit can hide additional rows. Public response limit fields echo the accepted request limit as a stringified decimal value.

The ontology primary key for notification policies is `notification_policies.policy_id`. Public command responses use `notification_policy_id` as the stable response field name for that same value. Wherever this contract says a response, `item.show` element, reminder result, or work-instance linkage returns `notification_policy_id`, the value is exactly the referenced `notification_policies.policy_id`; handlers must not synthesize a second policy identity. Internal ordering and persisted-row descriptions may still name `policy_id` when referring directly to the ontology column.

Each successful write command commits all rows that branch creates in one transaction, including canonical rows, audit rows, generated work rows, and the required command receipt. A failed command leaves no partial canonical mutation. Runtime workers may later create side-effect attempts, but authoring commands never send externally.

### Response Shape Catalog

This catalog defines reusable public response fragments. When a command references one of these names, the response returns the named fields at the stated location, not an implementation-defined object.

`item_shell` fields are `item_id`, `item_type`, `current_version`, `status`, `created_at_utc`, `updated_at_utc`, and optional `archived_at_utc` when stored. `common_version` fields are `version`, `title`, optional `summary`, optional `source_ref`, `intent_hash`, `normalized_fields_hash`, `created_at_utc`, and `created_by_subject_id`. `version_triplet` fields are `target_version`, `version`, and `current_version`; on fresh version-creating mutation, `version` and `current_version` are the new version, and on no-op or replay they remain the stored current version. `audit_identity` is `audit_id`. `receipt_identity` is `command_receipt_id`.

`event_detail` fields are `event_status`, `all_day`, `start_anchor_id`, embedded `start_anchor`, optional `end_anchor_id`, optional embedded `end_anchor`, optional `visibility`, and optional `attendance_policy_ref`. `task_detail` fields are `task_status`, optional `due_anchor_id`, optional embedded `due_anchor`, optional `defer_until_anchor_id`, optional embedded `defer_until_anchor`, optional `completed_at_utc`, optional `completed_by_subject_id`, optional `completion_state`, and optional `priority`. Embedded temporal anchors use the temporal-anchor output object defined earlier in Section 4.

`occurrence_event_detail` fields are `event_status`, `all_day`, concrete value-only `start_anchor`, and optional concrete value-only `end_anchor`. `occurrence_task_detail` fields are `task_status`, concrete value-only `due_anchor`, and optional concrete value-only `defer_until_anchor`. These virtual-occurrence fragments are distinct from persisted `event_detail` and `task_detail`: their anchor objects contain `anchor_kind` and the concrete scheduling fields for that kind, but never `anchor_id` or `created_at_utc`, because occurrence expansion creates no temporal-anchor rows.

`location_element` fields are `location_id`, `item_location_id`, `role`, `item_locations.created_at_utc`, and embedded location facts `label`, `kind`, optional canonical location fields when stored, `locations.created_at_utc`, and `locations.updated_at_utc`. `subject_role_element` fields are `item_subject_role_id`, `subject_id`, `role`, `status`, and `created_at_utc`. `notification_policy_element` fields are `notification_intent_id`, `notification_schedule_id`, `notification_policy_id`, optional `source_notification_policy_id`, recipient-owner facts, `channel`, `delivery_target_id`, `target`, normalized `schedule`, `normalized_notification_schedule_hash`, `late_handling`, `status`, `created_at_utc`, `created_by_command_id`, and optional `disabled_at_utc`.

`item.show` returns top-level fields `ok=true`, `command=item.show`, all `item_shell` fields, `current_common` containing `common_version`, exactly one of `event_detail` or `task_detail` when the current item type has that MVP detail table, `locations`, `subject_roles`, `notification_policies`, `locations_limit`, `locations_truncated`, `subject_roles_limit`, `subject_roles_truncated`, `notification_policies_limit`, and `notification_policies_truncated`. When `include_relations=true`, it also returns `relations`, `relations_limit`, and `relations_truncated`; when false, those three relation fields are omitted. `locations`, `subject_roles`, and `notification_policies` arrays contain the corresponding catalog element shapes.

`item.list` returns top-level fields `ok=true`, `command=item.list`, `items`, `limit`, and `truncated`. Each `items` element contains all `item_shell` fields, `current_common` containing `common_version`, and `detail_status`. `detail_status` is `event_status` for events, `task_status` for tasks, and omitted for item types without an MVP detail status.

`item.occurrences` returns the exact `spine.item-occurrences.recurrence.v1` shape in `contracts/schemas/recurrence-occurrence-response.schema.json`: `ok=true`, `command=item.occurrences`, item identity, current base-item `title`, current/source version and shell lifecycle facts, recurrence set and revision identities, decimal-string revision number, normalized recurrence-set hash, time-basis facts, canonical range facts, accepted decimal-string `limit`, `has_more`, nullable `next_cursor`, ordered `occurrences`, and ordered `diagnostics`. The top-level `title` is the exact current coordination-item title and is not changed by occurrence detail patches. Each occurrence contains stable original-schedule identity, current revision and source evidence, original and expressed scheduled facts, expressed schedule key, `virtual=true`, `actionable`, optional timezone-resolution and override facts, and exactly one of `occurrence_event_detail` or `occurrence_task_detail`. Ordinal and query-window position are not occurrence identity or response facts.

`event.update` fresh success returns `ok=true`, `command=event.update`, `updated=true`, `item_id`, `item_type=event`, `version_triplet`, shell `updated_at_utc`, `current_common`, `event_detail`, `audit_id`, and `command_receipt_id`. No-op and compatible replay success return the same fields except `updated=false`, omit `audit_id`, and keep the unchanged shell `updated_at_utc`; `command_receipt_id` is the fresh no-op receipt for a new no-op and the stored receipt for replay.

`event.reschedule` fresh success returns `ok=true`, `command=event.reschedule`, `rescheduled=true`, `item_id`, `item_type=event`, `version_triplet`, shell `updated_at_utc`, `current_common`, `event_detail`, `audit_id`, and `command_receipt_id`. No-op and compatible replay success return the same fields except `rescheduled=false`, omit `audit_id`, and keep the unchanged shell `updated_at_utc`; `event_detail` returns the stored current event anchors and accepted `all_day`.

`task.update` fresh success returns `ok=true`, `command=task.update`, `updated=true`, `item_id`, `item_type=task`, `version_triplet`, shell `updated_at_utc`, `current_common`, `task_detail`, `subject_roles`, `audit_id`, and `command_receipt_id`. No-op and compatible replay success return the same fields except `updated=false`, omit `audit_id`, and keep the unchanged shell `updated_at_utc`; `subject_roles` is the complete current task role set using `subject_role_element`, and `command_receipt_id` is the fresh no-op receipt for a new no-op and the stored receipt for replay.

Archived items are immutable for MVP command-authoring purposes. After request-shape validation, reference resolution, compatible same-`command_id` replay, and explicit duplicate-safe success checks that create no canonical item rows, every write command that targets an existing item must require each target item shell to have `coordination_items.status=active` before creating any new item version, relation, reminder policy, work instance, audit row, or command receipt. This rule applies to `event.update`, `event.reschedule`, `event.cancel`, `task.update`, `task.complete`, `task.cancel`, `relation.create` for both source and target endpoints, and `reminder.create`; `item.archive` uses its own terminal lifecycle duplicate rule. `reminder.create if_absent=true` duplicate-safe success may create only its command receipt after duplicate matching, even when the target item has since been archived, because it creates no canonical item row and represents a no-op retry of an existing reminder. A non-replay write against an archived item fails with `ok=false`, the command identifier, `error.code=invalid_state_transition`, `error.field=status`, a stable message naming archived item immutability, and CLI exit `2`, and leaves no partial mutation.

Item-typed commands fail closed when the resolved target item exists but has the wrong `coordination_items.item_type`. `event.update`, `event.reschedule`, and `event.cancel` require `item_type=event`; `task.update`, `task.complete`, and `task.cancel` require `item_type=task`. A wrong-type target fails before mutation with `ok=false`, the command identifier, `error.code=wrong_item_type`, `error.field=item_id`, a stable message naming the expected and actual item type, and CLI exit `2`. This check applies after compatible same-`command_id` replay checks and before stale-version rejection. `relation.create`, `item.archive`, and `reminder.create` are not event/task-typed commands in MVP and do not use this failure rule.

## 5. CLI Adapter Rules

The CLI adapter accepts `--db <path>` unless the command is pure help or version output. It accepts `--input <path>` or `--input -`, `--pretty`, and `--dry-run`; it accepts `--if-absent` for commands that support duplicate-safe create behavior. It accepts `--openclaw-whatsapp` as the MVP local binding switch that supplies the normalized OpenClaw WhatsApp adapter binding for reminder authoring. It may expose `--generate-command-id` only as an explicit operator convenience for JSON write requests that omit `command_id`. For the MVP CLI contract, options are supported before command words; post-command option placement is outside the stable invocation surface and may follow raw `argparse` behavior.

For `reminder.create channel=whatsapp`, the CLI must resolve its local OpenClaw configuration before invoking the command handler and pass the normalized `context.adapter_bindings.openclaw` object defined in Section 3. The command handler never reads CLI flags, process environment, OpenClaw client state, or adapter discovery directly. If the CLI cannot construct the normalized present binding object, the handler-visible context is missing the binding and the command fails with the Section 14 `environment_failure` result.

`spine --db <path> system info` is the read-only environment-discovery command. It requires an initialized current ledger because it reports both runtime and ledger authority. Its request is exactly an empty JSON object; when `--input` is omitted, this command alone supplies that empty object without reading stdin. An explicitly supplied `--input` is still parsed and validated normally. It returns `ok=true`, `command=system.info`, `response_contract=spine.system-info.v1`, runtime version, implemented and actual ledger-schema versions as canonical decimal strings, the exact installed timezone-database version required by local schedule authoring, and the sorted implemented contract-version array. It writes no ledger row and invokes no adapter. The exact response shape is `contracts/schemas/system-info-response.schema.json`.

Caller-supplied `command_id` is the stable MVP path. When `--generate-command-id` is implemented, the CLI derives the value as `cmd_<sha256>` over Spine canonical JSON containing `derivation_version=spine.cli-command-id.v1`, canonical `command`, the JSON request body excluding `command_id`, and the CLI-resolved database path string. The CLI-resolved database path string is the absolute lexical path formed by resolving `--db` relative to the process current working directory when needed, removing `.` and `..` path segments, preserving filesystem spelling and case, preserving symlink path spelling without resolving symlink targets, and omitting trailing separators except for filesystem root. Generated-ID tests must cover equivalent relative and absolute spellings that normalize to the same lexical path; symlink spellings are distinct unless their supplied lexical path also normalizes to the same string.

CLI path and input preflight failures occur before command-handler invocation and return one structured JSON response when transport control is recovered. Missing `--db`, unreadable input files, invalid JSON, non-object request JSON, and unavailable database paths fail with CLI exit `3`. The CLI must not create, initialize, or migrate a ledger as part of ordinary command invocation; ledger creation and migration remain explicit `spine-ledger-migrate --initialize-if-empty` behavior outside this command adapter. A `--db` path is available only when it names an existing initialized SQLite Spine ledger at a supported schema version. The MVP adapter distinguishes availability through existence, access, SQLite open, and schema verification checks; unavailable database paths return `ok=false`, include `command` after deterministic command resolution, report `error.code=invalid_request`, `error.field=db`, and exit `3`. A CLI invocation whose command words do not map to a supported canonical command returns the unsupported-command structured failure from Section 3 and exits `2`; if the CLI can recover a canonical dotted identifier from input, it echoes that value in `command`, otherwise it omits `command`. Success writes JSON to stdout and reserves stderr for human-readable diagnostics only. `--pretty` changes only whitespace.

## 6. Replay, Receipts, and Copy-Forward Identity

Same-`command_id` replay is part of every write command. After basic request-shape validation and before stale-version rejection, a write handler checks `command_receipts` for a completed invocation with the supplied `command_id`. Compatible replay returns `ok=true`, creates no new canonical rows, emits no external send, returns prior stable identities, and sets effect booleans such as `created`, `updated`, `archived`, `cancelled`, `completed`, or `rescheduled` to `false`.

Compatibility means the existing command receipt matches command identifier, command-derived IDs, immutable operation facts, actor, timestamps, target item/version facts, result identity facts, and command-specific semantic content. If the same `command_id` resolves to a receipt for the same command but requested facts conflict, the handler fails before mutation with `semantic_conflict`.

A command receipt is the durable replay identity and query index for every successful write outcome that consumes a `command_id`. It records command, `command_id`, actor, timestamp inputs, target item/version facts when relevant, operation facts, effect booleans, resulting identities, and enough command-specific semantic content to evaluate replay compatibility. It is not a side-effect attempt.

Fresh successful mutating commands still write command-derived audit rows where command-specific sections require audit rows, but replay compatibility is checked against `command_receipts`, not by querying audit payloads. For audit-writing branches, `result_identity_facts` includes the generated `audit_id`; for branches that intentionally write no audit row, such as `reminder.create if_absent=true` duplicate-safe success, `result_identity_facts` omits `audit_id` and includes the generated `command_receipt_id`. Compatible replay compares the stored receipt facts and returns stored result identities with the command effect boolean set to `false`; incompatible same-command replay fails with `semantic_conflict` before mutation.

Terminal lifecycle duplicate handling is shared by `item.archive`, `event.cancel`, `task.complete`, and `task.cancel`. Same-command compatible terminal requests replay successfully and return prior stable identities with the command effect boolean set to `false`. A terminal duplicate with a different `command_id` is not replay in the MVP and fails against the current terminal state with `invalid_state_transition`; the MVP does not classify different-command terminal duplicates into compatible and incompatible semantic subtypes. Terminal lifecycle duplicate checks occur before stale-version rejection.

The MVP command receipt storage artifact is `command_receipts`. Required stored fields are `command_receipt_id`, `command`, `command_id`, `actor_subject_id`, `action_timestamp_utc`, optional `item_id`, optional `target_version`, `effect`, `result_identity_facts`, `semantic_facts_hash`, `semantic_facts`, and `created_at_utc`. `command_receipt_id` is a text command-derived ID using row role `command_receipt` and request path `/`. `command` and `command_id` are text, `actor_subject_id` is text, timestamps are UTC timestamp strings, `item_id` is nullable text, `target_version` is a nullable text public version string when present, `effect` is text, and `result_identity_facts` and `semantic_facts` are canonical JSON objects. `semantic_facts_hash` is the Spine canonical hash of `semantic_facts`. `command_id` is unique across `command_receipts`; implementations must support lookup by `command_id` before fresh mutation. If an existing receipt has the same `command_id`, the handler compares the stored command and semantic facts for compatible replay and otherwise fails with `semantic_conflict`. For `subject.upsert`, `command_receipts.action_timestamp_utc` is always the request `updated_at_utc` for fresh insert, changed update, no-op, and compatible replay comparison; the persisted subject `created_at_utc` is a result fact, not a separate request fact. Unless a command states a narrower rule, `command_receipts.created_at_utc` equals `action_timestamp_utc`.

Allowed `command_receipts.effect` values are the response effect boolean name plus result state: `subject_created`, `subject_updated`, `subject_noop`, `item_archived`, `event_created`, `event_updated`, `event_update_noop`, `event_rescheduled`, `event_reschedule_noop`, `event_cancelled`, `task_created`, `task_updated`, `task_update_noop`, `task_completed`, `task_cancelled`, `relation_created`, `reminder_created`, `reminder_duplicate_noop`, `reminder_updated`, `reminder_edit_noop`, `reminder_disabled`, `reminder_disable_noop`, `notification_work_created`, `notification_work_reconciled`, `notification_work_all_retained`, `notification_work_zero_selected`, and `schedule_created`, plus the closed recurrence and provenance effects registered by `specs/recurrence.md`. `schedule_create_replay` is a response-branch effect only and MUST NOT be persisted in `command_receipts.effect`; the `schedule.create` receipt summary continues to report the stored `schedule_created` value during compatible replay. `result_identity_facts` must contain only stable response reconstruction identities, including `command_receipt_id`, command-specific item/version/work/relation identities, `audit_id` when an audit row was created, and generated identities that the corresponding success response returns. `semantic_facts` must contain replay comparison facts for the receipt-producing command: command, command id, actor, action timestamp, target item/version facts when relevant, normalized request facts, generated or referenced identities, resulting persisted facts, and effect booleans. For notification commands this includes version constants, intent and policy identities, normalized target/schedule/late-handling facts, schedule hash, recurrence provenance when present, and effect-specific work-id arrays. Stored receipt semantic facts are the sole authority for deciding compatible same-command replay.

All write-command success branches use `command_receipts` for same-command replay and global command-ID collision detection. No-op `event.update`, no-op `task.update`, no-op `event.reschedule`, and `reminder.create if_absent=true` duplicate-safe success create no item version or audit row, but still create one command receipt.

Copy-forward identity assigns copied version-scoped rows to the new version with request paths under `/copy_forward/<row_role>/<prior_id>`. Copied rows preserve semantic content but receive new derived row IDs. Copied supporting rows set `item_id` to the target item, `version` to the new version, and `created_at_utc` to the mutation action timestamp. Lifecycle-only mutations that carry forward unchanged temporal anchors reuse the existing anchor IDs.

Copied event and task detail rows preserve only ontology-backed detail facts. Event cancellation and task cancellation timestamps are command/audit replay facts and are reflected in the item shell `updated_at_utc` for the cancellation version; they are not persisted on `event_details` or `task_details`. Task completion remains ontology-backed on `task_details.completed_at_utc` and is copied forward unchanged when a completed task detail row is copied.

## 7. Supporting-Set Command Inputs

The ledger and read response shapes preserve locations, subject roles, and notification policies as canonical item-version supporting sets, and `item.show` returns existing persisted supporting rows using the Section 4 catalog shapes. The Agent Command Contract MVP does not accept initial `locations` or `notification_policies` arrays on `event.create` or `task.create`, and does not accept `subject_roles` on `event.create`. Supplying one of those deferred top-level fields fails request-shape validation with `unsupported_field`, the supplied field name, and CLI exit `2`.

`task.create` promotes the narrow task assignment slice through optional top-level `subject_roles`. `task.update` promotes the same slice through optional `patch.subject_roles`. Each value is an array of objects with required non-empty `subject_id` and `role`, plus optional `status` defaulting to `active`. The only accepted roles in this slice are `assignee` and `owner`; the accepted statuses are `active` and `inactive`. Every referenced subject must exist. A duplicate `(subject_id, role)` pair in one accepted array fails before mutation with `invalid_request`, `field=subject_roles` for create or `field=patch.subject_roles` for update, and CLI exit `2`.

The accepted array is the complete task assignee/owner role set for the resulting item version. On create, omission and an empty array both produce no task assignee/owner rows. On update, omission preserves the complete current role set by copy-forward, an empty array clears it, and a non-empty array replaces it. Replacement does not alter non-assignee/non-owner roles already present through lower-level ledger APIs; those rows copy forward unchanged. Role comparison is set-semantic and independent of request array order. A role-only patch whose normalized `(subject_id, role, status)` set already equals the current task assignee/owner set is a no-op.

Command-created task role rows use row role `item_subject_role`. Create IDs derive from `/subject_roles/<zero-based-index>` and update replacement IDs derive from `/patch/subject_roles/<zero-based-index>`. Task create and update success responses return `subject_roles` as the complete current task role set using the Section 4 `subject_role_element` shape. Other supporting-set authoring remains deferred; its future command paths remain reserved under `/locations`, `/subject_roles`, and `/notification_policies`.

## 8. Subject Commands

`subject.upsert` ensures a canonical subject exists. Minimum input fields are `command_id`, caller-supplied stable `subject_id`, `subject_kind`, `display_name`, `status`, `updated_at_utc`, and `actor_subject_id`. The supplied `subject_id` is the persisted `subjects.subject_id`; it is not command-derived and has no produced-row `row_role` or prefix.

Bootstrap is allowed only when no subjects exist and `actor_subject_id` equals `subject_id`. Otherwise the actor must resolve before mutation. Fresh upsert inserts the subject with supplied facts and sets both `subjects.created_at_utc` and `subjects.updated_at_utc` to request `updated_at_utc`. For an existing subject, `subjects.created_at_utc` is immutable ledger state and is not supplied by the request. Existing-subject upsert updates `subject_kind`, `display_name`, `status`, and persisted `updated_at_utc` when one of those three descriptive facts differs; if the descriptive facts already match, it is a no-op and the request `updated_at_utc` is recorded only as the command receipt action timestamp. The command writes a command receipt for fresh inserts, changed updates, and no-op outcomes.

Fresh insert success returns `ok=true`, `command=subject.upsert`, `created=true`, `updated=false`, `subject_id`, `subject_kind`, `display_name`, `status`, `created_at_utc`, `updated_at_utc`, and `command_receipt_id`. Existing-subject changed update success returns the same fields with `created=false`, `updated=true`, persisted subject facts after mutation, and the fresh `command_receipt_id`. Existing-subject no-op success returns persisted subject facts with `created=false`, `updated=false`, creates no subject row update, and returns the fresh `command_receipt_id`. Compatible same-command replay returns stored result facts and original `command_receipt_id` with `created=false` and `updated=false`; incompatible same-`command_id` replay fails with `semantic_conflict` before mutation.

`subject_group.upsert` ensures a canonical group exists for first-class group delivery and other group-owned coordination surfaces. Minimum input fields are `command_id`, `actor_subject_id`, caller-supplied stable `group_id`, `group_kind`, `display_name`, and `updated_at_utc`; `status` is optional and defaults to `active`. `group_kind` accepts `household`, `project`, `team`, and `transport_group`. `status` accepts `active` and `inactive`. Fresh insert and update response shape mirrors `subject.upsert` with `command=subject_group.upsert`, `group_id`, `group_kind`, `display_name`, `status`, timestamps, `created`, `updated`, and `command_receipt_id`.

`delivery_target.upsert` ensures an explicit adapter delivery endpoint exists without treating transport addresses as subjects. Required fields are `command_id`, `actor_subject_id`, `delivery_target_id`, `owner_kind`, `channel`, `adapter_name`, `target_ref`, and `updated_at_utc`; `display_name`, `account_id`, and `status` are optional, with `status` defaulting to `active`. For `owner_kind=subject`, exactly `owner_subject_id` must be supplied and must resolve. For `owner_kind=subject_group`, exactly `owner_group_id` must be supplied and must resolve. Once a target is referenced by notification policy or work rows, routing identity fields (`owner_kind`, owner ID, `channel`, `adapter_name`, `account_id`, and `target_ref`) cannot be changed by upsert; display and status changes remain valid. Fresh insert and update response shape returns the persisted owner, channel, adapter, account, target, display, status, timestamp facts, `created`, `updated`, and `command_receipt_id`.

## 9. Item Commands

`item.show` requires `item_id`. Optional request fields are `include_relations`, `locations_limit`, `subject_roles_limit`, `notification_policies_limit`, and `relations_limit`. `include_relations` defaults to `false`; every limit defaults to `50`, may be any integer from `0` through `100`, and fails with `invalid_request`, `field=<limit field>`, and CLI exit `2` when invalid. Missing items fail with `referenced_row_not_found`, `field=item_id`, and CLI exit `4`. It does not mutate.

`item.show` success returns the exact `item.show` response shape from the Section 4 Response Shape Catalog. Item types without an MVP detail table omit both `event_detail` and `task_detail`.

`item.show` returns `locations`, `subject_roles`, and `notification_policies` using the catalog element shapes. When `include_relations=true`, it returns `relations` elements in the `relation.list` response shape. It always returns the accepted requested limits as stringified decimal response fields and the truncation booleans named in the catalog.

`item.list` accepts optional request fields `item_type`, `status`, `limit`, and `include_archived`. Valid `item_type` filter values are `event`, `task`, `project`, and `collection`. Valid `status` filter values are shell statuses `active` and `archived`. Invalid filters fail before read execution with `unsupported_field`, `field=item_type` or `field=status`, and CLI exit `2`. `include_archived` defaults to `false`; when `status` is absent, `include_archived=false` returns only active items and `include_archived=true` returns both active and archived items. `status` and `include_archived` are mutually exclusive request fields: if `status` is supplied and `include_archived` is also supplied, the command fails before read execution with `invalid_request`, `field=include_archived`, and CLI exit `2`. `limit` defaults to `50`, may be any integer from `0` through `100`, and fails with `invalid_request`, `field=limit`, and CLI exit `2` when invalid. Items order by `coordination_items.updated_at_utc` descending, then `item_id` ascending. The success response is the exact `item.list` response shape from the Section 4 Response Shape Catalog. It does not mutate.

`item.occurrences` requires `item_id`, canonical inclusive `range_start`, and canonical exclusive `range_end`; optional fields are decimal-string `limit`, `cursor`, `range_basis`, and `include_diagnostics`. `range_basis` is `original_schedule` or `expressed_time` and defaults to `original_schedule`. `limit` defaults to `"100"` and is bounded by `1..1000`. Endpoint formats, the 3660-day or UTC-equivalent range limit, timezone behavior, diagnostic order, pagination order, and cursor binding follow `specs/recurrence.md`. The item must be an event with recurrence on its current start anchor or a task with recurrence on its current due anchor. Expansion is read-only and bounded; it creates no item versions, recurrence rows, provenance rows, work, projections, audit rows, or side-effect attempts.

`item.archive` requires `command_id`, `item_id`, `target_version`, `actor_subject_id`, and `archived_at_utc`. Compatible replay and terminal duplicate archive checks occur before stale-version rejection. A fresh archive requires the item to be active and current at `target_version`, sets shell `status=archived`, `archived_at_utc`, and `updated_at_utc`, writes an audit row and command receipt, and creates no new item version. Fresh success returns `ok=true`, `command=item.archive`, `archived=true`, `item_id`, `item_type`, `target_version`, `version` equal to the unchanged current item version, `current_version`, shell `status=archived`, `archived_at_utc`, shell `updated_at_utc`, `audit_id`, and `command_receipt_id`. Compatible same-command replay returns stored result identities and stored `command_receipt_id` with `archived=false` and creates no new audit row, command receipt, or item version.

Cancelled event/task detail copied into later versions preserves ontology-backed terminal status for deterministic output. The accepted cancellation timestamp remains available from command/audit replay facts and the cancellation version shell `updated_at_utc`, not from copied detail rows.

## 10. Recurrence Commands

`specs/recurrence.md` is authoritative for normalization, identity preimages, target resolution, effects, replay comparison, lineage, and transaction semantics. `contracts/schemas/recurrence-command.schema.json` is the machine-readable request-envelope contract. Unimplemented recurrence identifiers fail with `unsupported_command` before request-specific validation and without mutation; an implemented command rejects unimplemented fields with `unsupported_field`. An implementation slice is not a different recurrence model and MUST NOT persist a lossy approximation.

All recurrence-truth write commands require `command_id`, `actor_subject_id`, `item_id`, `target_version`, `recurrence_set_id`, `recurrence_revision_id`, and their command-specific UTC action timestamp. Same-command receipt lookup and cross-command command-id collision checks precede fresh stale-version validation. A fresh changed write atomically creates the next contiguous item version, matching detail and supporting rows, recurrence revision, normalized segments and children, lineage, audit row, and command receipt. No-op and replay branches create no recurrence revision. No recurrence command performs an external send.

- `recurrence.instance.add` requires `added_at_utc` and `scheduled_fact`; optional fields are `segment_id`, normalized detail patches, and `reason_code`. It produces an rdate or, for a duplicate occurrence with a patch, an occurrence override.
- `recurrence.instance.remove` requires `removed_at_utc`, `target_occurrence_key`, and `reason_code`; optional `segment_id` narrows validation. It creates an exdate and supersedes any active override for the excluded target.
- `recurrence.instance.override` requires `overridden_at_utc`, `target_occurrence_key`, and at least one move, detail-patch, or lifecycle field; optional fields are `segment_id` and `reason_code`.
- `recurrence.series.edit` requires `edited_at_utc`, `edit_scope`, and `recurrence_patch`. `target_occurrence_key` is required for `one` and `this_and_following` and forbidden for `whole_series`. Patch arrays have complete-replacement semantics within the selected scope.
- `occurrence_provenance.regenerate` requires `regenerated_at_utc`, `consumer`, `range_start`, and `range_end`; optional fields are `producer`, `range_basis`, and non-empty `occurrence_keys`. It updates provenance and report management state atomically but creates no item version, recurrence revision, work, attempt, or external send.

Successful recurrence responses return the closed `changed` and `effect` values, item and recurrence freshness facts, normalized recurrence-set hash, command receipt id, and branch-specific generated identities required by `specs/recurrence.md`. Compatible replay returns the stored result facts byte-for-byte. Stale item version precedes stale recurrence revision when both are stale.

## 11. Event Commands

`event.create` requires `command_id`, `actor_subject_id`, `created_at_utc`, `title`, `all_day`, and `start_anchor`; optional fields are `summary`, `source_ref`, `end_anchor`, `visibility`, and `attendance_policy_ref`. Initial supporting-set arrays are deferred by Section 7 and are not accepted MVP request fields. It creates one active `coordination_items` row with `item_type=event`, version 1 common facts, exactly one `event_details` row with `event_status=scheduled`, temporal anchors that satisfy all-day or timed-event rules, an audit row, and a command receipt. Fresh success returns `ok=true`, `command=event.create`, `created=true`, `item_id`, `item_type=event`, `version=1`, `current_version=1`, `current_common` containing the Section 4 `common_version` fields, `event_detail` containing the Section 4 `event_detail` fields, `audit_id`, and `command_receipt_id`. Compatible same-command replay returns the same stored identities and persisted facts with stored `command_receipt_id`, `created=false`, and creates no additional rows.

`event.update` requires `command_id`, `item_id`, `target_version`, `actor_subject_id`, `updated_at_utc`, and `patch`. The target must have shell `status=active`, `item_type=event`, and the supplied current `target_version`; it does not require a particular event detail status beyond the archived-shell, wrong-type, and stale-version rules. The MVP patch whitelist is limited to common item facts `title`, `summary`, and `source_ref`; patch field values, null clearing, wrong-type failures, and no-op normalization use the common Section 4 patch value contract. Empty or semantically no-op accepted patches return `updated=false`, create no version or audit row, and persist a command receipt. Fresh changes create the next version, copy forward unchanged supporting rows and anchors, write a new `event_details` row, update the item shell, and write an audit row and command receipt. Fresh, no-op, and compatible replay success responses use the exact `event.update` response shapes from the Section 4 Response Shape Catalog.

`event.reschedule` replaces temporal anchors in a new item version. For a non-recurring event it moves that concrete event and may attach a newly authored recurrence set at `start_anchor.recurrence_set`. Once an event owns a recurrence set, per-occurrence and series changes use the Section 10 recurrence commands; `event.reschedule` MUST NOT mutate that set's immutable identity facts or silently create a continuation set. It requires `command_id`, `item_id`, `target_version`, `actor_subject_id`, `rescheduled_at_utc`, `all_day`, and replacement `start_anchor`; replacement `end_anchor` and common-field `patch` are optional. The target must have shell `status=active`, `item_type=event`, supplied current `target_version`, and current detail `event_status=scheduled`. The optional `patch` uses the same common item fact whitelist and Section 4 patch value contract as `event.update`. A target whose current `event_status=cancelled` fails without mutation with `invalid_state_transition`, `field=event_status`, and CLI exit `2`. A reschedule that changes no anchor facts and has no common-field change returns `rescheduled=false` without version or audit row and persists a command receipt. Fresh reschedule creates the next version, replaces event detail anchors, applies the accepted patch result to common item fields, copies forward unchanged supporting rows, updates the shell, and writes an audit row.

Fresh, no-op, and compatible replay success responses use the exact `event.reschedule` response shapes from the Section 4 Response Shape Catalog. When `patch` is absent, common facts and hashes are copied from the target version and still returned in `current_common`.

`event.cancel` requires `command_id`, `item_id`, `target_version`, `actor_subject_id`, and `cancelled_at_utc`. The target must have shell `status=active`, `item_type=event`, supplied current `target_version`, and current detail `event_status=scheduled`. Fresh cancellation creates the next version with `event_status=cancelled`, copies forward common facts, locations, roles, notification policies, and temporal anchors, updates the item shell timestamp, and writes an audit row and command receipt. Fresh success returns `ok=true`, `command=event.cancel`, `cancelled=true`, `item_id`, `item_type=event`, `target_version`, resulting `version`, `current_version`, shell `updated_at_utc`, `audit_id`, and `command_receipt_id`. The accepted `cancelled_at_utc` remains a command/audit replay fact and is reflected in shell `updated_at_utc`; it is not a public lifecycle response field. Compatible same-command replay returns stored result identities and stored `command_receipt_id` with `cancelled=false`.

## 13. Relation Commands

`relation.create` requires `command_id`, `source_item_id`, `source_target_version`, `target_item_id`, `target_target_version`, `relation_type`, `actor_subject_id`, and `created_at_utc`. Both items must resolve, both endpoint item shells must be active for non-replay creation, and both endpoint shells must still be current at their supplied target versions. Same-`command_id` compatible replay is checked before stale endpoint-version rejection. If either endpoint current version differs from its supplied target version, the command fails before mutation with `ok=false`, `command=relation.create`, `error.code=stale_version`, `error.field=source_target_version` for a stale source endpoint or `error.field=target_target_version` for a stale target endpoint, and CLI exit `5`; if both endpoints are stale, the source field is reported. Stored MVP relation types are `depends_on` and `part_of`. MVP create requests reject input aliases `blocks` and `contains` with `unsupported_field`, `field=relation_type`, and CLI exit `2`. Unknown relation types are rejected with the same failure shape. Fresh create persists `relation_status=active`, `created_by_subject_id=actor_subject_id`, writes an audit row and command receipt, and returns `ok=true`, `command=relation.create`, `created=true`, `relation_id`, `source_item_id`, `source_target_version`, `source_current_version`, `target_item_id`, `target_target_version`, `target_current_version`, `relation_type`, `relation_status=active`, `created_at_utc`, `created_by_subject_id`, `audit_id`, and `command_receipt_id`. Compatible same-command replay returns stored identities, endpoint version facts, and stored `command_receipt_id` with `created=false`. An already-active identical stored relation created by a different command is not replay and fails with `semantic_conflict`, `field=relation`, and CLI exit `6`.

`relation.list` requires at least one of `item_id`, `source_item_id`, `target_item_id`, or `bounded=true`. Optional request fields are `item_id`, `source_item_id`, `target_item_id`, `relation_type`, `direction`, `include_derived_aliases`, `bounded`, and `limit`. `direction` defaults to `both` when `item_id` is supplied and may be `source`, `target`, or `both`; it is invalid with explicit source or target filters and fails with `invalid_request`, `field=direction`, and CLI exit `2`. The `relation_type` filter accepts stored types `depends_on` and `part_of`; when `include_derived_aliases=true`, it also accepts derived query aliases `blocks` and `contains`. Unknown relation types fail with `unsupported_field`, `field=relation_type`, and CLI exit `2`. If no item bound is supplied and `bounded` is absent or false, the request fails with `missing_required_field`, `field=item_id`, and CLI exit `2`. `limit` defaults to `50`, may be any integer from `0` through `100`, and fails with `invalid_request`, `field=limit`, and CLI exit `2` when invalid. Results include only active stored relations plus requested derived aliases and order by returned `relation_type`, returned `source_item_id`, returned `target_item_id`, then `relation_id`. The success response returns `ok=true`, `command=relation.list`, `relations`, `limit` as a stringified decimal value, and `truncated`. It does not mutate.

Every `relations` element has the same top-level keys unless a field is explicitly optional here: `relation_id`, `relation_type`, `source_item_id`, `target_item_id`, `relation_status`, `created_at_utc`, `created_by_subject_id`, `result_kind`, and `derived`. For stored rows, `result_kind=stored`, `derived=false`, `relation_id` is the stored `coordination_item_relations.relation_id`, `relation_type` is the stored type, endpoints are the stored endpoints, status and creator fields are copied from the stored relation, and derivation fields are omitted. For derived aliases, `result_kind=derived_alias`, `derived=true`, `relation_id` remains the stored relation ID that produced the alias, `relation_status`, `created_at_utc`, and `created_by_subject_id` are copied from that stored row, and the element additionally includes `derived_from_relation_id`, `derived_from_relation_type`, `derived_source_item_id`, and `derived_target_item_id`. A stored `depends_on` row from A to B may produce a derived `blocks` alias from B to A; a stored `part_of` row from A to B may produce a derived `contains` alias from B to A. For those alias elements, returned `source_item_id` and `target_item_id` are the swapped alias endpoints, `derived_source_item_id` and `derived_target_item_id` are the original stored endpoints, `derived_from_relation_id` is the stored relation ID, and `derived_from_relation_type` is the stored relation type. Stored rows and derived aliases are separate result elements; a derived alias never hides or rewrites the stored row when both are selected by the filters.

## 14. Reminder Commands

`specs/notifications.md` is the semantic authority for notification intent, schedule normalization, opportunity identity, work materialization, reconciliation, and delivery freshness. The machine request shapes are `contracts/schemas/notification-authoring.schema.json` and `contracts/schemas/notification-command.schema.json`.

`reminder.create` requires `command_id`, `actor_subject_id`, `item_id`, `target_version`, `created_at_utc`, an explicit recipient owner, `channel`, `delivery_target_id`, and the structured `notification` object using `authoring_contract=spine.notification-schedule-authoring.v1`; optional `if_absent` is the only additional field. The delivery target must be active, owned by the recipient, use the requested channel, and select the OpenClaw adapter. Authoring persists one logical intent and its first immutable policy revision, advances the item version, writes audit and receipt facts atomically, creates no work or side-effect attempt, and invokes no adapter.

Notification targets use `event_start` or `task_due` and exactly one application scope: `item` for a concrete non-recurring anchor, `each_occurrence` for every occurrence of a recurring anchor, or `selected_occurrence` with a current actionable `target_occurrence_key`. Schedules are exactly `once`, `offsets`, or bounded `repeat_window`; late handling is exactly `skip` or `deliver_within`. Their complete value domains, defaults, identities, validation order, and failure semantics are defined in `specs/notifications.md`.

`reminder.create` persists intent and policy truth only. Opportunity expansion and work materialization are separate bounded commands, so policy authoring never implies eager or unbounded work generation.

Duplicate-safe create uses the exact semantic identity in `specs/notifications.md`. With `if_absent=true`, a matching current active intent returns `effect=reminder_duplicate_noop`, existing intent/schedule/policy identities, and a new receipt while creating no item version, policy, work, attempt, or audit row. Without `if_absent=true`, a matching different-command intent fails with `semantic_conflict`, `field=notification`.

`reminder.create` returns `created`, `item_id`, `item_type`, target/result/current versions, `notification_intent_id`, `notification_schedule_id`, `notification_policy_id`, `normalized_notification_schedule_hash`, `audit_id`, and `command_receipt_id`. It returns the normalized accepted target, schedule, late-handling, recipient, channel, and delivery-target facts. It returns no work identity because policy authoring is not opportunity materialization or adapter preparation.

`reminder.edit` requires `command_id`, `actor_subject_id`, `item_id`, `target_version`, `notification_intent_id`, current `notification_policy_id`, `updated_at_utc`, and non-empty `patch`. The closed patch keys are recipient-owner facts, `channel`, `delivery_target_id`, `target`, `schedule`, and `late_handling`. Arrays and schedule objects use complete replacement, not merge or append. Supplying any recipient-owner field requires the complete replacement cluster: `recipient_kind` plus exactly its matching subject or group id; omitted recipient-owner fields copy the prior cluster only when none of them is supplied. A changed edit atomically creates the next item version and successor policy row for the same intent, copies all other supporting facts, writes audit and receipt facts, and returns `effect=reminder_updated`. A set-equivalent normalized patch returns `effect=reminder_edit_noop` and creates no item version or policy row.

`reminder.disable` requires `command_id`, `actor_subject_id`, `item_id`, `target_version`, `notification_intent_id`, current `notification_policy_id`, and `disabled_at_utc`; optional `reason_code` is audit evidence. A fresh change creates the next item version with a disabled successor policy row and returns `effect=reminder_disabled`. An already-disabled compatible command returns `effect=reminder_disable_noop`. V1 defines no re-enable command.

`notification.opportunities` is the read-only bounded expansion command defined by `specs/notifications.md`. Its request and exact `spine.notification-opportunities.v1` response use the notification command and opportunity-response schemas. It never writes policies, work, attempts, projections, or audit rows.

`notification_work.materialize` requires the bounded range, target version, command/actor/item identities, and `materialized_at_utc` defined by the notification command schema. Optional `notification_intent_id` narrows selection; optional `notification_opportunity_ids` selects a subset that MUST belong to the same computed result. Its closed effects are `notification_work_created`, `notification_work_reconciled`, `notification_work_all_retained`, and `notification_work_zero_selected`. It writes work, reconciliation, audit, and receipt facts atomically, invokes no adapter, and creates no side-effect attempt.

For all notification writes, same-command compatible replay and global command-id collision checks precede stale target-version validation. Validation then follows the exact order in `specs/notifications.md`. Dry run returns deterministic would-be identities for the selected branch and persists nothing.

## 14.1 Composite Schedule Command

`schedule.create` is the one-call operator surface for creating a new scheduled event or task, its complete initial notification-policy set, optional recurrence provenance, and optional bounded notification work. `specs/schedule-create.md` is its semantic authority; `contracts/schemas/schedule-create-request.schema.json` and `contracts/schemas/schedule-create-response.schema.json` are its structural request and response contracts.

The command creates policies directly on item version `1` and returns one composite audit and one composite command receipt. It does not obtain atomicity by invoking public subcommands or creating lower-level command receipts. A bounded recurring branch regenerates `notification_schedule` occurrence provenance before opportunity expansion. Any requested policy, provenance, expansion, materialization, or commit failure rolls back the item and every child row.

Delivery resolution accepts an existing explicit target or a named normalized context default. It never creates or approves a route. Materialization accepts a bounded local or item-relative horizon and performs UTC normalization internally. No branch starts work, writes a side-effect attempt, invokes an adapter, or reports delivery.

This subsection specifies future behavior only. The current MVP runtime acceptance boundary below remains the implemented low-level command family until `schedule.create` is separately declared implemented.

## 15. Dry Run and External Send Boundary

Every MVP write command must support the common `dry_run` context flag. Dry run runs the same deterministic validation, replay compatibility checks, stale-version checks, archived-item immutability checks, lifecycle validation, duplicate detection, generated-ID derivation, and output construction that the corresponding non-dry-run write would run before commit. Dry runs persist nothing and call no external systems.

Every handler-level dry-run response includes `dry_run=true` once a canonical command has been resolved. Dry-run success returns the same command-specific success shape as the corresponding non-dry-run branch, plus `dry_run=true`. For a fresh branch, generated IDs such as `item_id`, `audit_id`, `command_receipt_id`, temporal-anchor IDs, supporting-set row IDs, `notification_policy_id`, and `work_instance_id` are deterministic would-be identities derived exactly as the commit path would derive them; effect booleans such as `created=true`, `updated=true`, `archived=true`, `cancelled=true`, `completed=true`, and `rescheduled=true` mean the command would mutate if run without dry run. For compatible same-command replay branches that would create no rows, dry-run returns the same stored identities and false effect booleans as the non-dry-run branch, plus `dry_run=true`. For no-op and duplicate-safe `if_absent=true` branches whose non-dry-run path creates only a command receipt, dry-run returns the deterministic would-be `command_receipt_id`, false effect booleans, and `dry_run=true` without persisting that receipt. Dry-run failures after handler invocation return the normal structured failure shape with `dry_run=true`; CLI preflight failures that happen before command-handler invocation follow Section 5 and may omit `dry_run`.

Dry run never creates audit rows or command receipts, but it still returns the would-be `audit_id` or `command_receipt_id` when the equivalent non-dry-run success would create that artifact. A later non-dry-run invocation with the same request and context must return the same deterministic identities unless intervening ledger state changes cause a specified stale-version, duplicate, replay, lifecycle, archived-item, or semantic-conflict branch.

The agent authoring command interface does not send reminders externally. Runtime workers may process eligible work into adapter side effects only after durable work exists. Real sends remain guarded by explicit worker active mode, explicit sender choice, explicit allow-real-send opt-in, pre-write `side_effect_attempts` durability, stale-work guards, and adapter outcome recording.

## 16. Transport Adapter Requirements

Every transport adapter over this contract calls the same command handlers, preserves canonical dotted identifiers, request and response semantics, error names, stale-version behavior, archived-item immutability behavior, command-specific duplicate retry precedence, no-send authoring boundary, and exactly-one-structured-response discipline. Adapters must not introduce transport-specific business rules that make CLI, MCP, and HTTP behavior diverge.

## 17. MVP Acceptance Criteria

The contract is ready for implementation when agents can inspect the exact runtime, schema, timezone-data, and contract versions through `system.info`; bootstrap subjects; create, inspect, update, reschedule, complete, cancel, archive, and relate items; author task assignee/owner roles; use the canonical recurrence model for daily, weekly, monthly, yearly, interval, explicit-date, exclusion, override, occurrence, and series operations across local-date, local-instant, and UTC bases; regenerate occurrence provenance; and author one-time, explicit-offset, bounded elapsed-repeat, bounded local-calendar, and recurrence-bound notification policies. Notification acceptance includes policy-only authoring, bounded opportunity reads, idempotent work materialization, edit/disable lifecycle, reconciliation, occurrence-provenance freshness, Tickerd handoff, and fake delivery without direct authoring-time sends.

Write requests require stable caller-supplied `command_id`; CLI generated IDs are only explicit operator convenience and, when implemented, follow the deterministic CLI generated-command-ID rule in Section 5, including the normalized DB path string rule. Ordinary command-created row IDs derive deterministically from command ID, registered row-role prefixes, and command-defined request paths using the Section 4 produced-row identity registry; recurrence and structured-notification identities use their owning normative preimages. Every successful write outcome that consumes `command_id` creates one command receipt keyed by globally single-use `command_id`; cross-command reuse of a successful command ID fails with `semantic_conflict`, `field=command_id`, and CLI exit `6`. Compatible same-command replays create no duplicate canonical rows. Incompatible replays fail with `semantic_conflict`. Terminal lifecycle duplicates for archive, event cancellation, task completion, and task cancellation follow the shared Section 6 rule.

Stale target versions are rejected for updates, reschedule, lifecycle commands, recurrence writes, archive, relation creation for both endpoints, and reminder creation except for compatible replay, terminal lifecycle duplicate checks before stale-version rejection, and explicit `if_absent=true` reminder duplicate retry. Non-replay writes against archived items are rejected with `invalid_state_transition`, `field=status`, and no partial mutation; relation creation rejects archived source or target endpoints under the same rule. Successful item creates set shell `updated_at_utc=created_at_utc`; successful version-creating mutations advance shell `updated_at_utc` to their action timestamp; compatible replays and no-op commands do not advance it. Copied-forward supporting rows receive deterministic replacement identity and use Section 6 copy-forward field rules when existing supporting rows are carried by lower-level ledger state. Initial supporting-set authoring other than task assignee/owner roles remains deferred by Section 7 and is not part of this MVP acceptance boundary. Cancelled event/task detail copied into later versions preserves ontology-backed terminal status for deterministic `item.show` output. The accepted cancellation timestamp remains available from command/audit replay facts and cancellation version shell `updated_at_utc`, not from copied detail rows. Reminder-generated notification policies and work instances persist the Section 14 field-level defaults, exact `notification_policy_id` and `notification_policy_item_version` linkage, and created/updated timestamps equal to request `created_at_utc`.

Every successful write returns IDs, canonical command, current version, and audit/work identifiers where relevant; `command_receipts` is the authoritative replay index for all successful write outcomes. `reminder.create if_absent=true` duplicate-safe success is the explicit no-canonical-row exception: it creates only a command receipt, omits `audit_id`, and does not create an item version, notification policy, work instance, side-effect attempt, or external send. The Section 4 Response Shape Catalog defines exact public fields for `item.show`, `item.list`, `event.update`, `event.reschedule`, `task.update`, and reusable shell/common/detail fragments. Create command success responses for `event.create`, `task.create`, and `relation.create` are specified at field level, including effect booleans, generated identities, catalog-style `current_common` and detail objects where relevant, audit identity, and command receipt identity. Public response fields use `notification_policy_id` as the alias for `notification_policies.policy_id`. Lifecycle command success responses are specified at field level, including command receipt replay facts for compatible same-command replay. `relation.list` specifies filter validation, returned row fields, stored-versus-derived relation element schemas, derived alias provenance fields, ordering, limit defaults/ranges, and truncation semantics. Expected failures return structured JSON with exact MVP error code and normative CLI exit mapping, including the shared wrong-item-type failure for event/task commands. Dry-run responses are specified as normal branch response shapes plus `dry_run=true`, deterministic would-be IDs, and would-mutate effect semantics. No command performs an external send.

`subject.upsert` success responses are specified at field level for first-subject bootstrap, fresh subject insert, existing-subject changed update, no-op, and compatible replay, including `created`, `updated`, persisted subject facts, and command receipt identity. `event.update`, `event.reschedule`, and `task.update` success responses use the Response Shape Catalog for fresh changes, no-op outcomes, and compatible replay.

Tests cover command success, no-op, replay, collision, stale-version, lifecycle, wrong-type, unresolved-reference, unsupported-field, dry-run, atomicity, and CLI failure branches; deterministic row identity and receipts; common-field and supporting-set copy-forward; temporal-anchor validation; recurrence authoring/expansion/mutation/provenance; notification authoring/edit/disable/opportunity/materialization/reconciliation; and the no-send authoring boundary.
