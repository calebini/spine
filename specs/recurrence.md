# Spine Schedule-Based Recurrence

Status: Draft v0.4.0; executable v1 contract family implemented
Scope: Canonical recurrence-set model, deterministic expansion, occurrence mutation, command alignment, and downstream provenance
Authority: Normative flexible-recurrence target; runtime conformance requires matching persistence, command, fixture, and implementation declarations

Machine-readable contract family:

- `contracts/schemas/recurrence-types.schema.json`
- `contracts/schemas/recurrence-authoring.schema.json`
- `contracts/schemas/recurrence-set.schema.json`
- `contracts/schemas/recurrence-command.schema.json`
- `contracts/schemas/recurrence-occurrence-response.schema.json`
- `contracts/recurrence-fixture-manifest.json`

## 1. Purpose

Spine recurrence represents repeated schedule intent without turning a vendor calendar, daemon, runtime query, or adapter into the source of truth. Spine remains the canonical coordination ledger and planning fabric. External calendars, reminders, dashboards, local agents, and adapters are projections or consumers.

This contract defines one canonical recurrence model. Implementation MAY proceed in thin slices, beginning with daily local recurrence, but slice order does not create alternate recurrence models or durable semantic obligations. A partial runtime MUST fail unimplemented commands and fields explicitly and MUST NOT claim conformance with this contract until it implements the required surface.

Schedule recurrence is distinct from completion-relative routines such as one day after the prior task is completed. Completion-relative routine semantics are out of scope except that they MUST NOT be encoded as schedule recurrence.

## 2. Authority, Boundary, and Version Constants

The canonical recurrence set is stored on the temporal anchor that defines the schedule seed: `event_details.start_anchor_id` for an event and `task_details.due_anchor_id` for a task. The recurrence-bearing anchor owns a `recurrence_set` value.

The canonical recurrence model includes `time_basis` values `local_date`, `local_instant`, and `instant_utc`. This contract defines authoring, normalization, expansion, mutation, and provenance semantics for all three bases. An `instant_utc` recurrence uses a recurrence-bearing `instant_utc` event start or task due anchor, requires UTC scheduled facts, and omits `timezone` and `timezone_database_version`. It preserves a fixed global instant across civil-time offset changes; it does not preserve a local wall-clock hour.

The ontology, command contract, persistence model, and this recurrence contract MUST ratify the recurrence-bearing anchor and authoring surface atomically. `floating_local` recurrence remains out of scope until a timezone-free temporal-anchor shape is defined.

Normative recurrence version constants are `contract_version=spine.recurrence.contract.v1`, `normalization_version=spine.recurrence.normalization.v1`, and `canonical_json_version=spine.canonical-json.v1`. `spine.canonical-json.v1` is exactly the canonical JSON encoding defined by `specs/ontology.md`: valid UTF-8 JSON without insignificant whitespace; object keys sorted lexicographically by Unicode codepoint with duplicate keys forbidden; array order preserved; strings preserved without implicit normalization and invalid surrogate code points rejected; only `"`, `\`, and control characters U+0000 through U+001F escaped; control characters encoded as `\u00xx` with lowercase hexadecimal; shorthand escapes `\b`, `\f`, `\n`, `\r`, and `\t` forbidden; `/` never escaped; JSON numbers forbidden; absent optionals omitted; and explicit `null` preserved only where this contract's field schema permits it. Every recurrence-generated id, hash, cursor digest, receipt comparison hash, and report identity preimage MUST include `canonical_json_version`. The draft status and ratification lines are document metadata and MUST NOT enter recurrence hash preimages.

Recurrence MUST NOT be stored on an event end anchor, task defer-until anchor, notification-policy trigger anchor, or external projection.

### 2.1 Persistence Authority

The recurrence-bearing temporal anchor is the storage owner for canonical recurrence-set identity. Recurrence revisions, normalized segment facts, child facts, and lineage facts are immutable records associated with that set. A changed recurrence-authoring or recurrence-mutation command is also an item-version mutation: it MUST atomically create the next contiguous `coordination_item_versions` row, the matching immutable `event_details` or `task_details` row, the complete version-scoped supporting-row copy required by the ontology, the resulting recurrence revision and its normalized segment and child rows, the audit fact, lineage facts, and the command receipt. The same transaction updates `coordination_items.current_version` and sets the new recurrence revision's `source_item_version` to the created item version.

For events, the new `event_details.start_anchor_id` points to the recurrence-bearing start anchor associated with the recurrence set. For tasks, the new `task_details.due_anchor_id` does the same. When recurrence-set identity and seed-anchor facts are unchanged, the new detail row continues to reference the immutable recurrence-bearing anchor; revision-scoped facts are written as a new recurrence revision and MUST NOT be written into or over the prior anchor row. A command that changes a seed-anchor identity fact cannot mutate the same recurrence set and fails under the immutable set-identity rules in Section 5.

Stored item versions, event or task detail rows, version-scoped supporting rows, temporal anchors, recurrence revisions, segment rows, and recurrence child rows are immutable semantic facts. A recurrence mutation MUST NOT update any prior semantic row in place. Management fields whose one-way transition is explicitly defined by this contract, such as provenance supersession in Section 10, are the only mutable envelopes around an otherwise immutable fact. Projection state, adapter state, cursors, and command receipts cannot replace or override the recurrence-bearing item-version and recurrence-revision bundle as canonical recurrence truth.

## 3. Canonical Recurrence Set

A recurrence set has required fields `recurrence_set_id`, `recurrence_revision_id`, `revision_number`, `source_item_id`, `created_item_version`, `source_item_version`, `seed_anchor_id`, `time_basis`, `rules`, `rdates`, `exdates`, `overrides`, and `segments`. `timezone` and `timezone_database_version` are required for `local_date` and `local_instant`; both are absent for `instant_utc`. Integer fields are encoded as decimal strings in every hashed payload. A normalized recurrence set MUST contain at least one active rule or active rdate in an active segment.

Status fields are closed and hash-bearing. Rule, rdate, exdate, and override `status` values are `active` and `superseded`. Segment `status` values are `active`, `superseded`, and `retired`. `active` children participate in expansion and validation for the revision. `superseded` children and segments remain historical facts in the revision that superseded them but do not produce candidates, exclusions, or overrides. `retired` segments remain lineage facts whose range was closed by `this_and_following` or `whole_series` and do not produce candidates. No other child or segment status is legal. A command MUST NOT transition a stored child or segment in place; it writes the next recurrence revision with copied active facts, superseded or retired historical facts, and new active facts.

Rules have required `rule_id`, `segment_id`, `frequency`, `interval`, `seed`, `start_bound`, `end_condition`, and `status`; optional selectors are `by_month`, `by_month_day`, `by_weekday`, `by_set_position`, and `week_start`. Their value domains are closed:

- `frequency` is exactly one uppercase token: `DAILY`, `WEEKLY`, `MONTHLY`, or `YEARLY`.
- `interval` is a canonical decimal string in `1..2147483647`; omitted authoring input derives `"1"`.
- `seed` and `start_bound` are canonical scheduled-fact strings in the recurrence set `time_basis`. `seed` establishes recurrence phase and selector defaults. `start_bound` is inclusive, MUST be greater than or equal to `seed`, and filters the phased candidate stream without changing its phase.
- `end_condition` is exactly one of `{"kind":"unbounded"}`, `{"kind":"count","count":"N"}`, or `{"kind":"until","until":"scheduled_fact"}`. `count` is a canonical decimal string in `1..2147483647`. `until` is a canonical scheduled fact in the recurrence time basis, is inclusive, and MUST be greater than or equal to `start_bound`.
- `by_month` is a non-empty array of unique canonical decimal strings in `1..12`, sorted by numeric value.
- `by_month_day` is a non-empty array of unique canonical decimal strings in `-31..-1` or `1..31`, sorted by signed numeric value. Positive values count from the start of the month; negative values count backward from the end; nonexistent dates are omitted.
- `by_weekday` is a non-empty array of unique tokens from `MO`, `TU`, `WE`, `TH`, `FR`, `SA`, `SU`, sorted in that exact order.
- `by_set_position` is a non-empty array of unique canonical decimal strings in `-366..-1` or `1..366`, sorted by signed numeric value. It selects from the frequency-period candidate set after all other selectors and before duplicate collapse; positive positions count from the start and negative positions from the end.
- `week_start` is one weekday token. For `WEEKLY`, omission derives `MO`; the derived value is hash-bearing. Weekly interval periods begin on `week_start`.

`DAILY` permits interval and end condition only. `WEEKLY` permits `by_weekday` and `week_start`; absent `by_weekday` derives the seed weekday. `MONTHLY` permits exactly one selector family: `by_month_day`, `by_weekday`, or `by_weekday` plus `by_set_position`; `week_start` and `by_month` are forbidden. `YEARLY` permits optional `by_month` plus exactly one monthly selector family and forbids `week_start`; absent `by_month` derives the seed month. For `MONTHLY`, absence of every monthly selector derives `by_month_day=[seed day-of-month]`. For `YEARLY`, absence of every monthly selector derives `by_month_day=[seed day-of-month]`. Derived defaults are included in normalized payloads and hash preimages. For `instant_utc`, seed calendar components use UTC. For local recurrence, they use the local scheduled fact in the persisted timezone. Unsupported values or selector combinations fail with `invalid_request`, `field=rules[n].<field>` before normalization mutates anything.

Rdates have required `rdate_id`, `segment_id`, `scheduled_fact`, and `status`. Duplicate active rdates inside the same segment collapse by `(segment_id, scheduled_fact)` before rdate id derivation, occurrence source assignment, normalized hash construction, receipt comparison, and conformance vector evaluation. The surviving normalized revision contains exactly one active rdate for that pair. Collapsed duplicate active rdate inputs do not receive separate active ids and do not appear as separate occurrence sources. Superseded rdates remain lineage facts but do not produce candidates and never contribute occurrence sources.

Exdates have required `exdate_id`, `segment_id`, `target_occurrence_key`, `target_occurrence_selector`, `scheduled_fact`, `reason_code`, and `status`; optional lineage field `prior_target_occurrence_key` is present only when a copied exdate was retargeted to a changed selector. `target_occurrence_key` is the stable public key for the resolved original scheduled occurrence. `target_occurrence_selector` is the revision-independent selector defined in Section 5 and is the target fact used in normalized recurrence-set hash and child-id preimages. Exdates apply after original candidate production and duplicate collapse. Exdates never create replacements. For command-produced exdates, callers provide only `target_occurrence_key`; Spine resolves the current original occurrence, derives `target_occurrence_selector`, accepts a lineage key only when it maps uniquely to that selector, and derives `scheduled_fact` from the current original occurrence before exdate id derivation. A caller-supplied `scheduled_fact` on `recurrence.instance.remove` fails with `unsupported_field`, `field=scheduled_fact`. For stored recurrence-set materialization where both fields are present, `target_occurrence_key` MUST resolve to one current original occurrence whose canonical scheduled selector serializes to exactly the supplied `scheduled_fact`; mismatch fails before normalization, expansion, or persistence with `semantic_conflict`, `field=exdates[n].scheduled_fact`. When `prior_target_occurrence_key` is present, it is lineage evidence only and MUST map to the same current selector.

Overrides have required `override_id`, `segment_id`, `target_occurrence_key`, `target_occurrence_selector`, `override_kind`, `revision_key`, and `status`; optional fields are `prior_target_occurrence_key`, `expressed_scheduled_fact`, `common_detail_patch`, `event_detail_patch`, `task_detail_patch`, `lifecycle`, and `reason_code`. `target_occurrence_key` is the stable public key for the resolved original scheduled occurrence. `target_occurrence_selector` is the revision-independent selector defined in Section 5 and is used in normalized recurrence-set hash, override-id, and revision-key preimages. `prior_target_occurrence_key` is present only when a copied override was retargeted to a changed selector and is validated under Section 7. `revision_key` is a stable command-derived string unique for `(segment_id, target_occurrence_key)` within a recurrence revision after target-key resolution. Recurrence write requests MUST NOT accept caller-supplied `revision_key`; command paths derive it under Section 8 before override id derivation. At most one active override may target the same `(segment_id, target_occurrence_key)` in a recurrence revision.

Segments have required `segment_id`, `segment_index`, `active_start`, `source_revision_id`, and `status`; optional fields are `active_end`, `lineage_parent_segment_id`, `created_by_command_id`, and `reason_code`. `source_revision_id` is `initial` for a first persisted recurrence revision and otherwise names the prior stable recurrence revision that produced or copied the segment fact. `active_start` is inclusive and `active_end` is exclusive, both expressed as canonical scheduled facts in the recurrence set `time_basis`; `active_end` is omitted when unbounded. Active segment ranges MUST NOT overlap. Superseded and retired segment ranges MAY overlap active or non-active ranges because they are lineage-only facts.

Before `segment_index` is assigned, implementations construct `segment_preimage_key` for each segment from the Spine canonical JSON object containing exactly `active_start`, optional `active_end`, `source_revision_id`, `status`, optional `lineage_parent_segment_id`, optional `created_by_command_id`, and optional `reason_code`; it excludes both `segment_id` and `segment_index`. Segment indexes are zero-based decimal strings assigned by ascending `active_start`, then bytewise ascending canonical JSON encoding of this `segment_preimage_key`. If two segment key objects are byte-identical and their ranges cannot be distinguished after duplicate collapse, normalization fails with `semantic_conflict`, `field=segments[n]`. Only after this ordering step is `segment_index` added to the Section 3.1 normalized segment preimage.

Before normalized recurrence-set hash construction and before child id derivation, each child collection is sorted deterministically and request order is discarded. The sort key for every rule, rdate, exdate, and override is `segment_ref`, then the child semantic preimage key below encoded as Spine canonical JSON bytes, then the retained duplicate index for historical facts where duplicates are legal. Rule semantic preimage keys contain `frequency`, `interval`, `seed`, `start_bound`, `end_condition`, normalized selector fields, and `status`. Rdate semantic preimage keys contain `scheduled_fact` and `status`. Exdate semantic preimage keys contain `target_occurrence_selector`, optional `prior_target_occurrence_key`, command-derived or validated `scheduled_fact`, `reason_code`, and `status`. Override semantic preimage keys contain `target_occurrence_selector`, optional `prior_target_occurrence_key`, `override_kind`, command-derived `revision_key`, optional expressed scheduled fact, optional normalized detail patches, optional lifecycle, optional reason code, and `status`. Duplicate indexes are zero-based decimal strings assigned only within byte-identical semantic preimage keys that survive normalization as distinct historical facts; active duplicates that the contract requires to collapse never receive multiple active child ids. Input array order is never hash-bearing unless this contract explicitly adds an input-order field to one of these closed preimages.

Normalization validates fields in recurrence-set order, then segments, then `rules`, `rdates`, `exdates`, and `overrides`; validates closed statuses and legal status usage; removes direct ids from semantic child preimages; applies defaults; sorts enum arrays; collapses duplicate inclusions; orders segments and assigns segment indexes; resolves every authoring label or stored segment id to the normalized decimal-string `segment_ref`; constructs target-occurrence selectors only after that resolution; sorts child collections by the deterministic child ordering rule; derives ids; and emits canonical JSON with absent optionals omitted and no JSON numbers in hash preimages. No selector, child id, occurrence key, receipt fact, or provenance fact may be derived from a request-local or otherwise pre-index segment reference.

### 3.1 Normalized Recurrence-Set Hash Preimage

`normalized_recurrence_set_hash` is the lowercase SHA-256 digest of Spine canonical JSON for `normalized_recurrence_set_hash.v1`. Its preimage is a single object containing `derivation_version=normalized_recurrence_set_hash.v1`, `contract_version`, `normalization_version`, `canonical_json_version`, `recurrence_set_id`, `revision_number`, `source_item_id`, `created_item_version`, `source_item_version`, `seed_anchor_id`, `time_basis`, optional `timezone`, optional `timezone_database_version`, and the normalized `segments`, `rules`, `rdates`, `exdates`, and `overrides` arrays described below. Optional fields absent from the recurrence set are omitted from the preimage.

Direct generated identity fields are never included in this preimage: `recurrence_revision_id`, `segment_id`, `rule_id`, `rdate_id`, `exdate_id`, `override_id`, current `target_occurrence_key`, lineage row ids, occurrence ids, occurrence provenance ids, and side-effect attempt ids are omitted during first creation and every later revision. `recurrence_set_id` is included because it is derived or resolved before recurrence normalization and is stable across the series. Historical stable ids may appear only when they are reference facts rather than the identity of the object being hashed: `source_revision_id` after the first revision, `lineage_parent_segment_id`, and explicit `prior_target_occurrence_key` lineage references are included exactly where this contract names them. Current source rule and rdate ids are response and provenance evidence only; they are not normalized-set or occurrence-key identity facts. On first creation, `source_revision_id` is the literal string `initial` and `lineage_parent_segment_id` is absent.

Each segment preimage object contains `segment_index`, `active_start`, optional `active_end`, `source_revision_id`, `status`, optional `lineage_parent_segment_id`, optional `created_by_command_id`, and optional `reason_code`; it omits `segment_id`. Each rule, rdate, exdate, and override preimage replaces `segment_id` with `segment_ref`. Normalized `segment_ref` is exactly the canonical decimal-string `segment_index` of the target segment in this normalized revision; it is never a `segment_id` and is unrelated to the request-local `segment_label` used during authoring. The normalized `segments` array is ordered by `segment_index`. The normalized `rules`, `rdates`, `exdates`, and `overrides` arrays are ordered by the Section 3 child collection ordering rule, not by request order or storage order. Rule preimages contain frequency, interval, seed, start bound, end condition, normalized selector fields, status, and `rule_duplicate_index` only when required for a retained historical duplicate, but omit `rule_id`. Rdate preimages contain `segment_ref`, `scheduled_fact`, status, and `rdate_duplicate_index` only when required for a retained historical duplicate, but omit `rdate_id`. Exdate preimages contain `segment_ref`, `target_occurrence_selector`, optional `prior_target_occurrence_key`, `scheduled_fact`, `reason_code`, and status, but omit `exdate_id` and the current `target_occurrence_key`. Override preimages contain `segment_ref`, `target_occurrence_selector`, optional `prior_target_occurrence_key`, `override_kind`, command-derived `revision_key`, optional expressed scheduled fact, optional normalized detail patches, optional lifecycle, optional reason code, and status, but omit `override_id` and the current `target_occurrence_key`.

The identity derivation order MUST compute this hash after segment ordering, segment-index assignment, duplicate collapse, and deterministic child collection ordering, and before deriving `recurrence_revision_id`, `segment_id`, child ids, lineage ids, occurrence ids, provenance ids, cursor facts, and provenance content hashes. Conformance fixtures MUST publish the full canonical JSON preimage and digest, not only the digest.

### 3.2 Override Schema

`override_kind` is closed. Legal values are `move`, `detail_patch`, `lifecycle`, `move_detail_patch`, `move_lifecycle`, `detail_patch_lifecycle`, and `move_detail_patch_lifecycle`. Values containing `move` require `expressed_scheduled_fact`; values not containing `move` MUST omit it. Values containing `detail_patch` require at least one of `common_detail_patch`, `event_detail_patch`, or `task_detail_patch`; values not containing `detail_patch` MUST omit all detail patch objects. Values containing `lifecycle` require `lifecycle`; values not containing `lifecycle` MUST omit it. Illegal combinations fail with `invalid_request`, `field=override_kind` or the illegal payload field.

`common_detail_patch` is an object with optional `title`, `summary`, and `source_ref`. `title` MUST be a non-empty string when present and cannot be cleared. `summary` and `source_ref` MAY be strings or `null`; `null` clears the optional fact and is serialized as `null` inside the override patch preimage so the clear operation is hash-bearing. Omitted fields leave the occurrence detail unchanged.

`event_detail_patch` is legal only for event recurrence and is an object with optional `all_day` and `end_scheduled_fact`. `all_day` MUST be boolean when present. `end_scheduled_fact` MUST be either a canonical scheduled fact in the recurrence set `time_basis` or `null`; `null` clears the occurrence end expression. Event patches against task recurrence fail with `wrong_item_type`, `field=event_detail_patch`.

`task_detail_patch` is legal only for task recurrence and is an object with optional `defer_until_scheduled_fact` and `priority`. `defer_until_scheduled_fact` MUST be either a canonical scheduled fact in the recurrence set `time_basis` or `null`; `null` clears the occurrence defer-until expression. `priority` MAY be a string or `null`; `null` clears the occurrence priority overlay. Task patches against event recurrence fail with `wrong_item_type`, `field=task_detail_patch`.

`lifecycle` values are closed virtual overlay inputs. Events permit `active` and `cancelled`; tasks permit `active`, `completed`, and `cancelled`. Their mapping to authoritative occurrence detail output is exact: event `active -> event_status=scheduled`, event `cancelled -> event_status=cancelled`, task `active -> task_status=open`, task `completed -> task_status=done`, and task `cancelled -> task_status=cancelled`. Returned `occurrence_event_detail` and `occurrence_task_detail` fragments MUST use the authoritative ontology values, never the overlay vocabulary. `completed` on events, unknown lifecycle values, and lifecycle values inconsistent with the item type or current item state fail with `invalid_request`, `field=lifecycle`.

Lifecycle precedence and `actionable` are deterministic. Exdated occurrences are absent from expansion and have no `actionable` value. Every returned occurrence contains one JSON boolean computed by the first matching row:

| Precondition | Effective status | `actionable` |
| --- | --- | --- |
| item shell is archived | unchanged for inspection | `false` |
| base event is cancelled | `event_status=cancelled` | `false` |
| base task is done or cancelled | existing terminal `task_status` | `false` |
| event lifecycle override is cancelled | `event_status=cancelled` | `false` |
| task lifecycle override is completed | `task_status=done` | `false` |
| task lifecycle override is cancelled | `task_status=cancelled` | `false` |
| none of the above | base or active-overlay scheduled/open status | `true` |

An `active` overlay MUST NOT reopen an archived shell or terminal base detail and fails with `invalid_state_transition`, `field=lifecycle`. Lifecycle overlays affect downstream work eligibility but do not erase inspection expansion.

Detail patch objects are normalized by preserving only legal fields, sorting object keys by Spine canonical JSON rules, preserving `null` only for explicit clears, and omitting absent fields. An empty detail patch object after validation fails with `invalid_request`, `field=<patch>`. Override replay compares these normalized patch objects byte-for-byte.

## 4. Time Semantics

Timezone-bearing recurrence persists an IANA timezone and exact `timezone_database_version`. Unknown zones fail with `invalid_request`, `field=timezone`; unavailable pinned data fails with `environment_failure`, `field=timezone_database_version`. Replay MUST NOT substitute host timezone data.

Canonical scheduled facts are strings with exactly these encodings: `local_date` uses `YYYY-MM-DD`; `local_instant` uses `YYYY-MM-DDTHH:MM:SS` without offset or fractional seconds; `instant_utc` uses `YYYY-MM-DDTHH:MM:SSZ`. Years use four digits `0001..9999`. All components are zero-padded and MUST form a valid proleptic-Gregorian date and time. Lexicographic ordering is therefore chronological within one time basis. Cross-basis comparison is forbidden.

`local_instant` preserves local wall-clock intent across offset changes. DST nonexistent local candidates are omitted before occurrence identity, exclusions, or overrides; they do not consume `COUNT`. Ambiguous local times produce one original occurrence by selecting the earliest UTC instant among the valid offsets for that local wall-clock value in the pinned timezone database version. The selected occurrence `timezone_resolution` MUST include `timezone`, `timezone_database_version`, `resolution_kind`, `local_datetime`, `utc_instant`, and decimal-string `offset_seconds`; ambiguous selections use `resolution_kind=ambiguous_earliest_instant`, unambiguous selections use `resolution_kind=unambiguous`, and omitted nonexistent candidates may appear only in diagnostics with `resolution_kind=nonexistent_omitted`. If the pinned timezone database cannot enumerate the valid offsets for a local candidate or cannot distinguish an ambiguous local value from an unambiguous one, expansion fails before occurrence identity, cursor, or provenance derivation with `environment_failure`, `field=timezone_database_version`.

## 5. Identity and Occurrence Keys

Identity derivation order is fixed: derive or resolve `recurrence_set_id`; validate recurrence-set fields; verify that any mutation targeting an existing recurrence set preserves every `recurrence_set_id` preimage field byte-for-byte; apply selector defaults; order segments by `(active_start, segment_preimage_key)`; assign segment indexes; resolve authoring labels and stored segment ids to normalized decimal-string `segment_ref` values; collapse required active duplicates; build revision-independent original-occurrence selectors for any command or copied exdate/override targets from those normalized segment references; validate exdate target and scheduled-fact consistency against those selectors; reject range overlaps, duplicate bounds, and duplicate override revision keys after selector resolution; sort child collections by the Section 3 deterministic child ordering rule; compute `normalized_recurrence_set_hash` from the Section 3.1 preimage; derive `recurrence_revision_id`, `segment_id`, child ids, occurrence keys, lineage ids, and occurrence ids. Historical ids from prior revisions never change. The normalized recurrence-set hash and child ids MUST NOT depend on a value whose preimage includes `recurrence_revision_id`; only the revision-independent `target_occurrence_selector` may appear in those preimages.

Generated recurrence ids use `<prefix>_<sha256>` over Spine canonical JSON containing the exact preimage fields registered below. `target_occurrence_selector` is a prefix-free canonical JSON object, not a generated row id. Its derivation version is `spine.recurrence-target-occurrence-selector.v1`, and its fields are `recurrence_set_id`, normalized decimal-string `segment_ref`, canonical original `scheduled_fact`, `origin_kind`, `source_rule_selectors`, and `source_rdate_selectors`. Rule selectors use the normalized rule semantic preimage plus rule duplicate index when present; rdate selectors use normalized `scheduled_fact`, status, and rdate duplicate index when present after active duplicate collapse. The selector is built before `normalized_recurrence_set_hash` and `recurrence_revision_id`. Every preimage includes `derivation_version`, `contract_version`, `normalization_version`, and `canonical_json_version`. Optional fields are omitted when absent. Prior stable ids are included only as reference facts when the registry says so. Ambiguous, missing, duplicate-after-collapse, or contradictory preimage facts fail before id derivation with the error named for the owning semantic rule, usually `invalid_request` for malformed input or `semantic_conflict` for incompatible stored facts.

`occurrence_key` identifies one original scheduled occurrence independently of the recurrence revision that currently materializes it. It is derived from the revision-independent `target_occurrence_selector` and stays byte-for-byte stable while that selector stays equal. Rule edits, segment splits, or source changes that produce a different selector produce a new key and explicit prior/current lineage; merely creating a new recurrence revision does not. Exdate and override targets resolve a supplied current or lineage key to exactly one current selector before normalized hash construction and child-id derivation. A prior key used only for carry-forward remains an explicit `prior_target_occurrence_key` lineage reference and never replaces the selector in child-id preimages.

A persisted `recurrence_set_id` permanently binds the Section 5 preimage facts for that set: `source_item_id`, `seed_anchor_id`, `created_item_version`, `time_basis`, optional `timezone`, and optional `timezone_database_version`. Those facts are set-identity facts, not revision facts. A recurrence truth mutation that targets an existing `recurrence_set_id` MUST resolve the stored preimage and compare it against the requested or carried-forward facts before normalization, replay comparison, provenance freshness derivation, or child-id derivation. Any attempt to change one of those facts in place fails closed before mutation with `semantic_conflict`, `field=recurrence_set_id` for stored/requested id mismatch or `semantic_conflict`, `field=recurrence_patch` for a mutation patch that supplies a different preimage fact. Spine does not define recurrence-set replacement or continuation in this MVP; changing one of these facts requires a future explicit replacement artifact with its own scope, linkage, receipt, provenance, and conformance rules.

Identity registry:

- `recurrence_set_id`: prefix `recurrence_set`; `derivation_version=spine.recurrence-set-id.v1`; preimage fields are `source_item_id`, `seed_anchor_id`, `created_item_version`, `time_basis`, optional `timezone`, and optional `timezone_database_version`. A command may resolve an existing recurrence set by stored id only when those stored preimage facts match byte-for-byte. Fresh derivation fails with `semantic_conflict`, `field=recurrence_set_id` if the same source item and seed anchor already name a different active recurrence set. Existing-set mutation MUST NOT rederive the id from changed preimage facts, retain the old id with changed preimage facts, or create a replacement set as a side effect.
- `recurrence_revision_id`: prefix `recurrence_revision`; `derivation_version=spine.recurrence-revision-id.v1`; preimage fields are `recurrence_set_id`, `revision_number`, `normalized_recurrence_set_hash`, optional `prior_recurrence_revision_id`, and optional `command_id`. The first revision omits `prior_recurrence_revision_id`; later revisions include it as a reference fact.
- `segment_id`: prefix `recurrence_segment`; `derivation_version=spine.recurrence-segment-id.v1`; preimage fields are `recurrence_revision_id`, `segment_index`, `active_start`, optional `active_end`, `source_revision_id`, `status`, optional `lineage_parent_segment_id`, optional `created_by_command_id`, and optional `reason_code`. Copied historical segment ids from prior revisions remain references only; newly materialized segment ids derive from the new revision.
- `rule_id`: prefix `recurrence_rule`; `derivation_version=spine.recurrence-rule-id.v1`; preimage fields are `recurrence_revision_id`, `segment_ref`, `frequency`, `interval`, `seed`, `start_bound`, `end_condition`, normalized selector fields, `status`, and optional `rule_duplicate_index`. The duplicate index is a zero-based decimal string assigned only among normalized active or historical rule preimages that remain distinct after validation; if duplicate active rules would produce the same candidate stream in the same segment, normalization collapses them before id derivation.
- `rdate_id`: prefix `recurrence_rdate`; `derivation_version=spine.recurrence-rdate-id.v1`; preimage fields are `recurrence_revision_id`, `segment_ref`, `scheduled_fact`, `status`, and optional `rdate_duplicate_index`. Duplicate active rdates collapse by `(segment_ref, scheduled_fact)` and do not receive multiple active ids.
- `exdate_id`: prefix `recurrence_exdate`; `derivation_version=spine.recurrence-exdate-id.v2`; preimage fields are `recurrence_revision_id`, `segment_ref`, `target_occurrence_selector`, command-derived `scheduled_fact`, `reason_code`, and `status`. If `target_occurrence_key` cannot be resolved to one original occurrence through the Section 7 target-key resolution view, derivation fails with `semantic_conflict`, `field=target_occurrence_key`. Optional `prior_target_occurrence_key` is lineage evidence and is included in the normalized recurrence-set hash, receipt facts, and lineage payload, but it is not part of `exdate_id` derivation.
- `override_id`: prefix `recurrence_override`; `derivation_version=spine.recurrence-override-id.v2`; preimage fields are `recurrence_revision_id`, `segment_ref`, `target_occurrence_selector`, `override_kind`, command-derived `revision_key`, optional expressed scheduled fact, optional normalized detail patches, optional lifecycle, optional reason code, and `status`. Optional `prior_target_occurrence_key` is lineage evidence and is included in the normalized recurrence-set hash, receipt facts, and lineage payload, but it is not part of `override_id` derivation. At most one active override per `(segment_ref, target_occurrence_key)` may survive normalization.
- `revision_key`: prefix-free string `revkey_<sha256>`; `derivation_version=spine.recurrence-override-revision-key.v2`; preimage fields are `command_id`, `recurrence_set_id`, `prior_recurrence_revision_id`, `target_occurrence_selector`, `segment_ref`, and `override_path`. It is never accepted from the caller. `override_path` is the canonical override operation path defined in Section 8 and is derived after patch normalization.
- `lineage_id`: prefix `recurrence_lineage`; `derivation_version=spine.recurrence-lineage-id.v1`; preimage fields are `command_id`, `recurrence_set_id`, `prior_recurrence_revision_id`, `new_recurrence_revision_id`, `lineage_role`, optional `prior_segment_id`, optional `new_segment_id`, optional `prior_child_id`, optional `new_child_id`, `effect`, and `lineage_index`. The index is zero-based decimal in deterministic lineage output order.
- `occurrence_key`: prefix-free string equal to unpadded base64url of the canonical JSON preimage bytes, then `.`, then the lowercase hexadecimal SHA-256 digest of those same bytes; `derivation_version=spine.recurrence-occurrence-key.v2`; preimage field is `target_occurrence_selector`. `origin_kind` is closed: `rule`, `rdate`, or `union`. `origin_kind=rule` requires exactly one rule selector and no rdate selector; `origin_kind=rdate` requires exactly one rdate selector and no rule selector; `origin_kind=union` is required only when duplicate collapse merges multiple rule candidates or one or more rule candidates with the single surviving active rdate. Duplicate active rdates have already collapsed, and superseded rdates never contribute. Returned `source_rule_ids`, `source_rdate_ids`, and `source_entries` are current-revision evidence resolved from the stable selector; they are not occurrence-key preimage fields. Rule source entries contain `source_kind=rule`, current `source_id`, and the rule's zero-based decimal `rule_local_index`; the optional rdate entry contains `source_kind=rdate` and current `source_id`.
- `occurrence_id`: prefix `occurrence`; `derivation_version=spine.recurrence-occurrence-id.v2`; preimage fields are `occurrence_key`, `recurrence_revision_id`, `normalized_recurrence_set_hash`, `time_basis`, optional `timezone`, optional `timezone_database_version`, and selected timezone-resolution facts when applicable. Ordinal or page position is not an identity fact.
- `expressed_schedule_key`: prefix-free string equal to unpadded base64url of the canonical JSON preimage bytes, then `.`, then the lowercase hexadecimal SHA-256 digest of those same bytes; `derivation_version=spine.recurrence-expressed-schedule-key.v1`; preimage fields are `occurrence_key`, `range_basis`, canonical original `scheduled_fact`, canonical expressed scheduled fact, and optional active `override_id`. Detail-only and lifecycle-only overrides use the original scheduled fact as the expressed scheduled fact.
- `occurrence_provenance_slot_key`: prefix `occurrence_provenance_slot`; `derivation_version=spine.occurrence-provenance-slot.v1`; preimage fields are `consumer`, `item_id`, `recurrence_set_id`, canonical `range_basis`, canonical `range_start`, canonical `range_end`, and canonical original `scheduled_fact`. It is stable across recurrence revisions while the original scheduled slot remains in the selected range.
- `occurrence_provenance_id`: prefix `occurrence_provenance`; `derivation_version=spine.occurrence-provenance-id.v2`; preimage fields are `occurrence_provenance_slot_key`, optional `producer`, `source_item_version`, shell lifecycle facts, `recurrence_revision_id`, `normalized_recurrence_set_hash`, `occurrence_key`, original and expressed scheduled facts, timezone facts, current source id arrays and source entries, optional `override_id`, lifecycle, actionability, and the immutable recurrence-set identity preimage facts.
- `occurrence_provenance_content_hash`: no prefix; `derivation_version=spine.occurrence-provenance-content-hash.v2`; preimage fields are the full immutable provenance semantic snapshot excluding `occurrence_provenance_id`, management status, and any response-only sequence position.
- `cursor_digest`: no prefix; `derivation_version=spine.recurrence-cursor-digest.v2`; preimage is exactly the canonical cursor JSON bytes defined in Section 6, including version constants, item freshness facts, recurrence facts, canonical range facts, accepted `limit`, diagnostics flag, and last ordering tuple.

## 6. Expansion Semantics

Expansion is explicit, read-only, and bounded. The `item.occurrences` request requires `item_id`, `range_start`, and `range_end`; optional fields are `limit`, `cursor`, `range_basis`, and `include_diagnostics`. Reserved floating-local fields fail as `unsupported_field`. `limit` is a canonical decimal string in `1..1000`; omission derives `"100"`. Ranges are inclusive start and exclusive end.

`range_basis` is a closed enum with values `original_schedule` and `expressed_time`. Omitted `range_basis` defaults to `original_schedule` before request comparison, cursor creation, response serialization, occurrence-provenance identity derivation, and replay hashing; all persisted or returned range facts use this canonicalized value. Unknown `range_basis` values fail before expansion, cursor decoding, occurrence identity, provenance selection, or receipt derivation with `invalid_request`, `field=range_basis`.

`range_start` and `range_end` MUST serialize as canonical scheduled selectors in the recurrence set `time_basis`: `YYYY-MM-DD` for `local_date`, `YYYY-MM-DDTHH:MM:SS` for `local_instant`, and `YYYY-MM-DDTHH:MM:SSZ` for `instant_utc`. Local range values are interpreted in the recurrence set timezone and pinned `timezone_database_version`; they MUST NOT include timezone names, offsets, fractional seconds, or omitted seconds. UTC range values allow only `Z`, with no fractional seconds or numeric offsets. A range endpoint that cannot be parsed exactly in the selected time basis fails with `invalid_request`, `field=range_start` or `field=range_end`; a request whose end is not strictly greater than start in that basis fails with `invalid_request`, `field=range_end`. For `local_date` and `local_instant`, the range is too large when `range_end` is later than `range_start` plus 3660 proleptic-Gregorian calendar days, preserving the local time-of-day for `local_instant`. For `instant_utc`, the range is too large when elapsed time exceeds `316224000` seconds, exactly 3660 times 86400. A too-large range fails with `invalid_request`, `field=range_end`, `reason_code=range_too_large`. Implementations MUST NOT coerce a range endpoint between local and UTC domains, infer missing seconds, round, truncate, or substitute host timezone data.

Range filtering is deterministic and follows `range_basis`. For `original_schedule`, the inclusive/exclusive range predicate compares each surviving occurrence original scheduled fact after active segment filtering, original candidate production, duplicate collapse, and active exdate exclusion, but before active overrides, expressed-time ordering, detail shifting, cursor pagination, or downstream provenance writing. For `expressed_time`, the predicate compares the occurrence expressed scheduled fact after active move overrides are applied; occurrences without a move use their original scheduled fact as the expressed scheduled fact. Detail-only, lifecycle-only, event end, and task defer overlays do not change the range predicate. In both bases, `range_start <= selected_scheduled_fact < range_end`; occurrences outside the range retain stable keys but are not returned or selected for provenance regeneration.

Rule generation uses proleptic-Gregorian calendar periods anchored by `seed`. Period zero is the seed calendar day for `DAILY`, the `week_start`-based week containing the seed for `WEEKLY`, the seed calendar month for `MONTHLY`, and the seed calendar year for `YEARLY`. A period is active exactly when its zero-based period index is divisible by `interval`. Daily active periods yield the seed time-of-day on that calendar day. Weekly active periods yield every selected weekday in that week and sort the resulting dates chronologically. Monthly active periods apply the normalized non-positional monthly selectors inside that month, then apply `by_set_position` to the resulting month-period array when present. Yearly active periods visit normalized `by_month` values in numeric order, apply the normalized non-positional monthly selectors inside each visited month, collect the candidates into one year-period array, and then apply `by_set_position` once to that year-period array when present. `local_date` candidates contain only the selected date; `local_instant` and `instant_utc` candidates retain the seed hour, minute, and second. Candidates earlier than `seed`, earlier than inclusive `start_bound`, outside the active segment range, or later than an inclusive `UNTIL` bound are discarded. Invalid calendar dates and selector positions outside a period's candidate array are omitted rather than clamped or shifted.

Within each active period, selector candidates are sorted by canonical scheduled fact and deduplicated before `by_set_position`; positive positions are one-based from the start, negative positions are one-based from the end, and selecting the same candidate through more than one position produces it once. Rule-local candidates are then globally ordered by original scheduled fact. `COUNT` is rule-local and consumes only these valid, non-omitted candidates at or after `start_bound`, before active exdates, overrides, query-range filtering, or cross-source duplicate collapse. Once the count is consumed, that rule produces no later candidates. These steps also define `rule_local_index`: a zero-based decimal string assigned in this rule-local order before cross-source collapse. Implementations MAY use calendar arithmetic to seek directly to the first relevant period; they MUST NOT enumerate every earlier period merely to derive a response position or identity.

Cursors are opaque recurrence-page cursors: unpadded base64url of canonical cursor JSON followed by `.` followed by its lowercase SHA-256 digest. Cursor JSON binds version constants, item id, source item version, shell lifecycle facts, recurrence set and revision ids, normalized hash, canonical range facts (`range_basis`, `range_start`, and `range_end`), accepted decimal-string `limit`, diagnostics flag, recurrence-set identity preimage facts, and last ordering tuple. Repeated request facts must match cursor facts byte-for-byte after defaulting and range canonicalization. Changed item truth, shell lifecycle truth, recurrence truth, normalized hash, range facts, accepted limit, diagnostics flag, or recurrence-set identity preimage facts yield `stale_version`, `field=cursor`.

Expansion order is total and uses the same canonical `range_basis` enum. For `original_schedule`, order by original scheduled fact, occurrence key, then occurrence id. For `expressed_time`, order by expressed scheduled fact, expressed schedule key, occurrence key, then occurrence id. `UNTIL` is inclusive in the recurrence time basis.

Occurrence source identity is assigned in two stages. First, each rule candidate receives that rule's `rule_local_index` after rule-local duplicate collapse and before any cross-rule or rdate collapse. Second, all candidates with the same `(segment_ref, canonical original scheduled_fact)` are merged into one surviving original occurrence selector. If the set contains exactly one rule source and no rdate source, `origin_kind=rule`; if it contains exactly one rdate source and no rule source, `origin_kind=rdate`; otherwise `origin_kind=union`. Cross-rule overlaps and rule/rdate overlaps therefore produce one stable occurrence key whose current source arrays preserve every contributing active source. Duplicate active rdate inputs have already collapsed to one normalized active rdate, and superseded rdates do not contribute.

The canonical success response contract id is `spine.item-occurrences.recurrence.v1`.

A successful recurrence-aware bounded expansion response returns top-level fields `ok=true`, `command=item.occurrences`, `response_contract=spine.item-occurrences.recurrence.v1`, `item_id`, `item_type`, current item `title`, `current_version`, `source_item_version`, shell lifecycle facts, `recurrence_set_id`, `recurrence_revision_id`, `revision_number`, `normalized_recurrence_set_hash`, canonical `range_basis`, canonical `range_start`, canonical `range_end`, accepted decimal-string `limit`, `occurrences`, `has_more`, `next_cursor`, and `diagnostics`. `title` is the exact title from the current coordination item version selected by `current_version`; occurrence detail patches do not change this top-level base-item fact. Local-time responses also return `timezone` and `timezone_database_version`; `instant_utc` responses omit both. `has_more` is a JSON boolean. `next_cursor` is present as an opaque cursor string only when `has_more=true`; it is present as `null` when `has_more=false`. An empty result set is reported as `occurrences=[]`, `has_more=false`, and `next_cursor=null`. A final non-empty page uses the same terminal pagination facts. A non-final page MUST include a `next_cursor` whose cursor JSON binds the final returned occurrence ordering tuple.

Each occurrence element in `spine.item-occurrences.recurrence.v1` contains `occurrence_id`, `occurrence_key`, `virtual=true`, `recurrence_set_id`, `recurrence_revision_id`, `segment_id`, `origin_kind`, `source_entries`, `source_rule_ids`, `source_rdate_ids`, original scheduled fact, expressed scheduled fact, `expressed_schedule_key`, `range_basis`, `lifecycle`, `actionable`, optional `override_id`, and exactly one of `occurrence_event_detail` or `occurrence_task_detail` using the virtual detail fragments defined by the public command contract. Local-time occurrence elements include `timezone_resolution` for `local_instant` and timezone facts for `local_date`; `instant_utc` occurrence elements always omit timezone and timezone-database facts and return only canonical UTC scheduled facts. `source_entries`, `source_rule_ids`, and `source_rdate_ids` are current-revision evidence after duplicate collapse, not occurrence-key preimage fields. Detail-only and lifecycle-only overrides return the original scheduled fact as the expressed scheduled fact and still expose the active `override_id`.

`diagnostics` is an array. When `include_diagnostics` is omitted or false, it MUST be empty. When `include_diagnostics=true`, each diagnostic element contains `diagnostic_code`, `field`, `severity`, optional `scheduled_fact`, optional `timezone_resolution`, optional `source_id`, and optional `message`. Diagnostics are non-authoritative explanatory facts: they may report omitted nonexistent local candidates or pagination observations, but they MUST NOT change occurrence identity, ordering, cursor construction, provenance identity, or failure outcomes.

Diagnostic values are closed. Legal `diagnostic_code` values are `dst_nonexistent_omitted` and `pagination_observation`. Legal `severity` values are `info` and `warning`, ordered for diagnostics sorting as `warning` before `info`. `dst_nonexistent_omitted` always uses `severity=warning`, `field=timezone_resolution`, and includes `scheduled_fact`, the producing rule's `source_id`, and `timezone_resolution.resolution_kind=nonexistent_omitted`; one diagnostic is emitted per omitted rule candidate before cross-rule collapse. `pagination_observation` always uses `severity=info`, `field=limit`, and is emitted only when `has_more=true`. Diagnostic ordering is deterministic: severity order, then `diagnostic_code`, then `field`, then optional `scheduled_fact`, then optional `source_id`, all compared bytewise after canonical string serialization with absent optionals sorting before present optionals. A response, report, fixture, or replay artifact that contains an unknown diagnostic field, unknown `diagnostic_code`, unsupported `severity`, missing required diagnostic field, or a diagnostic class whose fixed severity or field does not match this contract is invalid and fails before artifact persistence or fixture acceptance with `invalid_request`, `field=diagnostics[n]` or the narrower invalid child field.

## 7. Mutation, Revision Lineage, and Occurrence Lifecycle

Every recurrence truth mutation creates a new recurrence revision unless the command resolves to compatible replay or a specified no-op. A fresh changed revision increments `revision_number` by one decimal string, carries forward unchanged active facts, writes superseded or retired facts needed for replay, derives new active facts, and updates `source_item_version` to the item version created by the mutation. Stored child and segment rows are immutable semantic facts inside a revision. The recurrence-set identity preimage facts named in Section 5 are immutable across all revisions of one recurrence set; mutation commands may advance `source_item_version` and revision-scoped facts, but they MUST NOT change `source_item_id`, `seed_anchor_id`, `created_item_version`, `time_basis`, `timezone`, or `timezone_database_version` for the targeted `recurrence_set_id`.

Carried-forward exdates and overrides MUST be retargeted deterministically before they participate in exclusion, override application, child ordering, normalized hashing, command receipt comparison, or command target validation. To build the target-key resolution view, Spine expands the prior revision's and draft revision's pre-exception original candidate streams after segment and child copy but before active exdates and overrides. It maps each prior selector to exactly one current selector by matching recurrence set, segment lineage, canonical original scheduled fact, origin kind, and semantic source selectors through the child-copy map. A target matching zero or more than one current selector fails before persistence with `semantic_conflict`, `field=target_occurrence_key`. When the selector remains equal, the occurrence key remains equal and no prior-key field is written. When the selector changes but lineage proves one successor, the copied child stores the successor key and selector plus the old key as `prior_target_occurrence_key`. Replay comparison includes both keys and the selector so historical intent cannot be silently rebound.

Target-key proof is always bounded. The canonical original `scheduled_fact` decoded from the occurrence-key selector determines the minimal half-open proof window: `[scheduled_fact, next local date)` for `local_date`, `[scheduled_fact, scheduled_fact plus one local wall-clock second)` for `local_instant`, and `[scheduled_fact, scheduled_fact plus one UTC second)` for `instant_utc`. Spine expands only that selector-local window in each compared revision. Failure to decode the scheduled fact, a basis mismatch, arithmetic overflow, absence from every active segment, or inability to form the exclusive endpoint fails with `semantic_conflict`, `field=target_occurrence_key`; implementations MUST NOT widen the window heuristically or perform unbounded expansion. When a command accepts an optional `range_hint`, the hint MUST contain canonical `range_start` and `range_end`, satisfy `range_start < range_end`, and contain the selector-local proof window. It may validate the proof but MUST NOT influence selector resolution; an invalid or excluding hint fails with `invalid_request`, `field=range_hint`.

`edit_scope` is closed: `one`, `this_and_following`, and `whole_series`. `one` requires `target_occurrence_key` and produces only an override or exdate/rdate change for that occurrence. `this_and_following` requires `target_occurrence_key`, resolves its original scheduled fact as the split point, retires the prior active segment at that split point, creates a following active segment beginning at that split point, copies applicable active children into the following segment under new ids, and applies the requested patch only to the following segment. `whole_series` applies the patch to all active segments and does not require `target_occurrence_key`.

For `this_and_following`, the child-copy predicate is closed. Active rules whose active segment range intersects `[split_scheduled_fact, prior_active_end)` are copied into the following segment with `start_bound` raised to the split scheduled fact when the prior bound is earlier. A copied rule retains its original `seed`, selector defaults, interval phase, and `UNTIL` bound. For a copied `COUNT` rule, Spine computes `produced_before_split` as the number of that rule's valid, non-omitted candidates from its original inclusive `start_bound` through candidates strictly before the split, before exdates, overrides, range filtering, or cross-source collapse. The copied rule's count is `original_count - produced_before_split`; a zero or negative remainder produces no active copied rule and records the omission in lineage. When the patch replaces the following `rules` collection, the supplied rules replace these would-be copies and their `COUNT` values are independent new rule-local counts. Active rdates with `scheduled_fact >= split_scheduled_fact` and inside the following segment range are copied; active rdates before the split are not copied; an active rdate exactly at the split is copied. Active exdates and overrides are copied only when their resolved original occurrence selector maps to a following-segment original occurrence at or after the split; targets before the split are omitted, targets at the split are copied and retargeted, and targets after the split are copied and retargeted. Superseded and retired facts are not copied as active children, though they remain historical lineage facts. Any copied child whose segment assignment, scheduled fact, or target selector cannot be represented in the following segment fails before persistence with `semantic_conflict`, `field=target_occurrence_key` for target-bearing children or `field=segments[n]` for non-target children. The receipt comparison facts include copied-child ids, omitted-child ids with effects, source-to-copy maps, target-key retarget maps, and every `COUNT` subtraction fact.

Invalid split targets fail with `semantic_conflict`, `field=target_occurrence_key` when the target key is not in the current revision, is excluded before overrides, belongs to a retired segment, or is outside the selected active segment. A `this_and_following` split at a segment `active_start` does not create an empty prior segment: the new revision writes the prior segment as `superseded`, creates exactly one active replacement segment with the same `active_start` and prior `active_end`, copies or replaces children under the closed rules above, and records prior-to-replacement lineage. It MUST NOT emit a zero-length retired segment. A split after the last surviving occurrence is invalid with `semantic_conflict`, `field=target_occurrence_key`.

Lineage output order is deterministic: segment close or retirement facts, following segment creation, copied rules, copied rdates, copied exdates, copied overrides, superseded prior children, replacement children, and audit facts; ties within a group order by prior stable id then new stable id. Lineage ids use the Section 5 registry. Lineage is returned on changed writes and stored in the recurrence command receipt comparison facts; dry runs return would-be lineage ids and payloads.

Occurrence lifecycle overlays are virtual until bound by occurrence provenance or a downstream work/projection record. A lifecycle override changes the mapped authoritative occurrence detail status, actionability, and downstream eligibility for that occurrence only under Section 3.2. It does not mutate the base item shell, event detail row, or task detail row. A cancelled occurrence remains inspectable unless a request explicitly filters lifecycle outside this contract; a completed task occurrence returns `task_status=done`, remains a recurrence occurrence, and is not actionable work.

## 8. Recurrence Command Contract Alignment

The canonical authoring surface version is `spine.recurrence-authoring.v1`. It adds a `recurrence_set` object at exactly `event.create.start_anchor.recurrence_set`, `event.reschedule.start_anchor.recurrence_set`, and `task.create.due_anchor.recurrence_set`; recurrence remains forbidden on every other anchor role. The authoring object requires `time_basis` and `rules`; optional fields are `timezone`, `timezone_database_version`, `rdates`, and `segments`. Generated ids, revision numbers, item/version facts, statuses, exdates, overrides, and lineage facts are forbidden on initial authoring. Omitted `segments` derives one active unbounded segment beginning at the seed scheduled fact. Omitted `rdates` derives an empty array. Because initial authoring forbids caller-supplied `exdates` and `overrides`, normalization also derives persisted empty `exdates=[]` and `overrides=[]` arrays before normalized hash construction, receipt comparison, and conformance vector generation. Initial rules and rdates are normalized with `status=active`; generated recurrence, segment, and child ids follow Sections 3 and 5. Exdates and overrides are authored after creation through the occurrence-targeted commands below so their target keys resolve against a persisted recurrence revision.

Each initial `rules` entry requires `frequency`, `seed`, `start_bound`, and `end_condition`; optional fields are `interval`, `by_month`, `by_month_day`, `by_weekday`, `by_set_position`, `week_start`, and `segment_label`. Each initial `rdates` entry requires `scheduled_fact` and may include `segment_label`. Each initial `segments` entry requires a request-local non-empty `segment_label` and `active_start`; optional fields are `active_end` and `reason_code`. Authoring `segment_label` values MUST be unique byte-for-byte, are resolved before canonical segment ordering, and are discarded before persistence and hash construction. When `segments` is omitted, rule and rdate entries MUST omit `segment_label`. When `segments` is present, every rule and rdate entry MUST contain `segment_label` naming exactly one authoring segment. Authoring entries MUST NOT contain generated ids, normalized `segment_ref` values, statuses, revision facts, lineage facts, or target-occurrence facts.

Authoring validates the recurrence-bearing anchor and `time_basis` together. `local_date` requires a `local_date` anchor plus `timezone` and `timezone_database_version`; `local_instant` requires a `local_instant` anchor plus the same timezone facts; `instant_utc` requires an `instant_utc` anchor, UTC seeds and bounds ending in `Z`, and absent `timezone` and `timezone_database_version`. A mismatch fails before item or recurrence persistence with `invalid_request`, `field=time_basis`.

Successful authoring is atomic with the owning item command. It creates the recurrence-bearing anchor, the item version, recurrence set, recurrence revision `1`, normalized active children and segments, audit fact, and command receipt together or creates none. The owning command receipt includes the authoring-surface version, normalized authoring object, normalized recurrence-set hash, recurrence-set identity preimage facts, and all generated recurrence identities. Compatible replay returns the same item and recurrence identities; incompatible replay fails under the owning command's command-id rule. Dry run returns the deterministic would-be identities and persists nothing.

Canonical recurrence command identifiers are `recurrence.instance.add`, `recurrence.instance.remove`, `recurrence.instance.override`, `recurrence.series.edit`, and `occurrence_provenance.regenerate`. A partial runtime that has not implemented one of these identifiers MUST fail it as `unsupported_command` before request-specific validation and without mutating recurrence truth or provenance.

All recurrence write requests share required `command_id`, `actor_subject_id`, `item_id`, `target_version`, `recurrence_set_id`, `recurrence_revision_id`, and one command-specific action timestamp. Request bodies MUST NOT contain `dry_run` or `revision_key`. Unknown fields fail with `unsupported_field` after command-identifier support and before stale-version checks. Field validation order is: command identifier support; top-level unknown fields; missing required common fields; timestamp format; actor and item reference resolution; same-command receipt lookup; cross-command command-id collision; recurrence-set identity preimage verification; target version freshness; recurrence set and revision freshness; command-specific semantic validation; id derivation; dry-run or commit.

Dry run inherits command-contract dry-run semantics exactly: it persists nothing, calls no external systems, and returns branch-equivalent success or failure with deterministic would-be identities.

Recurrence-truth mutation terminal successes return `ok=true`, `command`, item and target/current version facts, recurrence set id, prior and new recurrence revision ids, decimal-string revision number, command receipt id, `changed`, `effect`, `normalized_recurrence_set_hash`, and recurrence-set identity preimage facts. For fresh changed writes, the hash is the resulting new revision hash; those responses also return audit id and lineage ids. For no-op and compatible replay branches, the hash is the current unchanged recurrence-set hash from the stored result snapshot. `occurrence_provenance.regenerate` is a provenance-only command: it MUST NOT report a new recurrence revision unless another command changed recurrence truth, and its success shape is defined separately below.

Mutation `effect` values are closed and command-specific. `recurrence.instance.add` permits `instance_add_rdate_created`, `instance_add_override_created`, `instance_add_override_replaced`, and `duplicate_add_noop`. `recurrence.instance.remove` permits `instance_remove_exdate_created`, `instance_remove_exdate_created_override_superseded`, and `remove_noop_already_excluded`. `recurrence.instance.override` permits `instance_override_created`, `instance_override_replaced`, and `override_noop`. `recurrence.series.edit` permits `series_edit_one_excluded`, `series_edit_one_override_created`, `series_edit_one_override_replaced`, `series_edit_following_applied`, `series_edit_whole_applied`, and `series_edit_noop`. Every value ending in `_created`, `_replaced`, `_superseded`, `_excluded`, or `_applied` has `changed=true`; every value ending in `_noop` has `changed=false`. Compatible replay returns the stored pair byte-for-byte. Fresh execution MUST choose only from the values registered for that command after normalization and target resolution; any other success effect is nonconforming.

The recurrence command receipt is the durable replay index for recurrence write commands, including no-op successes and `occurrence_provenance.regenerate`. Its persisted replay index contains `command_receipt_id`, `command_id`, canonical `command`, `actor_subject_id`, the command-specific action timestamp field name and value, `item_id`, request `target_version`, request `recurrence_set_id`, request `recurrence_revision_id`, recurrence-set identity preimage facts, normalized request comparison facts, resolved target facts, result branch, `changed`, `effect`, resulting item version facts, prior and resulting recurrence revision facts, generated audit id when present, lineage ids when present, generated child or provenance ids when present, and a `replay_facts_hash` over the command-specific comparison object. Compatible same-command replay requires the stored canonical command and every command-specific comparison fact, including recurrence-set identity preimage facts, to match byte-for-byte after normalization. Cross-command `command_id` reuse fails with `semantic_conflict`, `field=command_id`, before stale checks. Same-command incompatible replay fails with `semantic_conflict`, `field=command_id`, before stale checks. Compatible replay returns the stored receipt and result identities, including the stored `changed` and `effect` values byte-for-byte, without creating item versions, recurrence revisions, provenance rows, audit rows, lineage rows, side-effect attempts, or external sends.

Override command paths derive a closed `override_path` before `revision_key` derivation and before override receipt comparison. `override_path` is a Spine canonical JSON object with `path_version=spine.recurrence-override-path.v1`, `has_move` as a JSON boolean, `detail_patch_fields` as a lexicographically sorted array of the present normalized patch object names from `common_detail_patch`, `event_detail_patch`, and `task_detail_patch`, and `has_lifecycle` as a JSON boolean. It is derived only from accepted request fields after detail patch normalization and `override_kind` derivation. A move-only override therefore has `has_move=true`, empty `detail_patch_fields`, and `has_lifecycle=false`; a detail-only override names the present patch objects and has `has_move=false`; lifecycle combinations set `has_lifecycle=true`. No caller-supplied `override_path` is accepted. Unknown or contradictory path facts fail through the owning request field, usually `invalid_request`, `field=override_kind` or `field=<patch>`.

Command-specific comparison facts are closed. `recurrence.instance.add` compares requested `scheduled_fact`, resolved or default `segment_id`, normalized optional detail patches, reason code, duplicate-detection result, and either the produced rdate facts or the duplicate-add-with-patch override target and normalized override facts. A duplicate add without a patch compares the resolved duplicate occurrence key and scheduled fact and records `effect=duplicate_add_noop`. `recurrence.instance.remove` compares requested target facts, resolved current-revision `target_occurrence_key`, `target_occurrence_selector`, optional `prior_target_occurrence_key` when carry-forward retargeting is involved, resolved segment, command-derived original `scheduled_fact`, reason code, produced exdate id and preimage, and the target occurrence identity facts used to derive that scheduled fact. `recurrence.instance.override` compares requested target facts, resolved current-revision target occurrence key, `target_occurrence_selector`, optional prior target key, resolved segment, derived `override_path`, override kind, command-derived `revision_key`, optional expressed scheduled fact, normalized detail patches, optional lifecycle, reason code, produced override id and preimage, and any superseded override id. `recurrence.series.edit` compares `edit_scope`, normalized `recurrence_patch`, required target occurrence key for `one` and `this_and_following`, selected segment, split scheduled fact for `this_and_following`, prior and following segment preimages, child copy maps including target-key retarget maps, superseded child facts, replacement active child facts, and lineage payload. `occurrence_provenance.regenerate` compares `consumer`, optional `producer`, range facts and selection facts, source item and shell freshness facts, recurrence-set identity preimage facts, recurrence revision and normalized hash facts, derived provenance content hashes, retained provenance ids, superseded provenance ids, newly written provenance ids, closed report ids, unresolved report facts, and the terminal `changed` and `effect` branch names exactly as returned in the success response.

`recurrence.instance.add` requires `added_at_utc` and `scheduled_fact`; optional fields are `segment_id`, `common_detail_patch`, `event_detail_patch`, `task_detail_patch`, and `reason_code`. `scheduled_fact` MUST match the recurrence set time basis. After same-command receipt resolution, Spine selects the unique active segment satisfying `active_start <= scheduled_fact` and either having no `active_end` or satisfying `scheduled_fact < active_end`. Equality with `active_start` is contained; equality with `active_end` is not. Zero containing segments fail with `semantic_conflict`, `field=scheduled_fact`; multiple containing segments fail with `semantic_conflict`, `field=segments`. When `segment_id` is supplied, it MUST name that selected segment or the command fails with `semantic_conflict`, `field=segment_id`.

Duplicate detection then evaluates the current normalized revision before constructing a draft rdate. If the scheduled fact duplicates a surviving occurrence, including one already backed by the active rdate for `(segment_ref,scheduled_fact)`, and no patch is supplied, the command is a changed=false no-op with `effect=duplicate_add_noop` and writes only a command receipt. If it duplicates a surviving occurrence and a patch is supplied, the command creates or replaces an override against that occurrence rather than an rdate: no prior active override yields `instance_add_override_created`; a structurally different prior active override yields `instance_add_override_replaced`; and a normalized patch equal to the stored active override yields `duplicate_add_noop`. Only a non-duplicate request constructs one new active rdate and returns `effect=instance_add_rdate_created`. Normalization collapse applies to duplicate inputs within the draft collection after this command-level decision; it MUST NOT convert a fresh request duplicating stored truth into a changed rdate write.

`recurrence.instance.remove` requires `removed_at_utc`, `target_occurrence_key`, and `reason_code`; optional field is `segment_id`. It MUST NOT accept caller `scheduled_fact`, patch objects, or lifecycle fields. The target key resolves against the current recurrence revision before exdate creation. Removing an already excluded occurrence is a changed=false no-op with `effect=remove_noop_already_excluded` if the same target and reason facts match; a different reason fails with `semantic_conflict`, `field=reason_code`. A valid fresh remove always supersedes any active override for that target because the exdate removes the occurrence before override application. It returns `instance_remove_exdate_created_override_superseded` when an override was superseded and `instance_remove_exdate_created` otherwise.

`recurrence.instance.override` requires `overridden_at_utc`, `target_occurrence_key`, and at least one of `expressed_scheduled_fact`, a detail patch, or `lifecycle`; optional fields are `segment_id` and `reason_code`. It derives `override_kind` and `override_path` from the supplied fields after patch normalization. No-op comparison is structural: only a normalized request byte-equal to the stored active override is `changed=false`, `effect=override_noop`. If no active override exists, an accepted request creates one with `effect=instance_override_created` even when its expressed values equal the current base occurrence, thereby preserving explicit intent against later base-item edits. A structurally different active override is superseded and replaced with `effect=instance_override_replaced`.

`recurrence.series.edit` requires `edited_at_utc`, `edit_scope`, and `recurrence_patch`; `target_occurrence_key` is required for `one` and `this_and_following` and forbidden for `whole_series`. Empty patches and set-equivalent normalized patches are changed=false no-ops with `effect=series_edit_noop`. A changed `one.exclude` returns `series_edit_one_excluded`; a changed `one.override` returns `series_edit_one_override_created` or `series_edit_one_override_replaced` according to prior structural state; a changed `this_and_following` edit returns `series_edit_following_applied`; and a changed `whole_series` edit returns `series_edit_whole_applied`. The identity fields `time_basis`, `timezone`, and `timezone_database_version` are never legal in `recurrence_patch`; supplying one fails before normalization with `unsupported_field`, `field=recurrence_patch.<field>`.

For `edit_scope=one`, `recurrence_patch` is a closed object containing exactly one of `exclude` or `override`. `exclude` is an object requiring non-empty `reason_code` and accepting no other fields; it normalizes to the same exclusion operation as `recurrence.instance.remove`. `override` is an object requiring at least one of `expressed_scheduled_fact`, `common_detail_patch`, `event_detail_patch`, `task_detail_patch`, or `lifecycle`, with optional `reason_code`; it uses the Section 3.2 field schemas and normalizes to the same override path as `recurrence.instance.override`. No implementation-defined convenience fields are permitted. `one` MUST NOT rewrite rules, rdates, segments, or any occurrence other than `target_occurrence_key`.

For `edit_scope=this_and_following` or `whole_series`, `recurrence_patch` is a closed object with optional array fields `rules`, `rdates`, `exdates`, and `overrides`; at least one array MUST be present. Each present array is a complete replacement of that active child collection within the selected scope; an omitted array copies that collection forward, while an empty array clears it. Prior active children in a replaced collection are written as superseded lineage facts. The resulting selected scope MUST still satisfy the invariant that at least one active rule or active rdate can produce occurrences.

Each `rules` entry requires `frequency`, `seed`, `start_bound`, and `end_condition`; optional fields are `interval`, `by_month`, `by_month_day`, `by_weekday`, `by_set_position`, and `week_start`, using Sections 3 and 4. Each `rdates` entry requires exactly `scheduled_fact` plus the scope-specific `segment_id` rule below. Each `exdates` entry requires `target_occurrence_key` and non-empty `reason_code`. Each `overrides` entry requires `target_occurrence_key` plus at least one Section 3.2 override field and may include `reason_code`. Callers MUST NOT supply generated ids, selectors, revision keys, status, lineage fields, or scheduled facts derived by exclusion targeting.

For `this_and_following`, child entries MUST omit `segment_id`; Spine assigns every replacement entry to the newly created following segment. For `whole_series`, every child entry MUST include `segment_id` naming an active segment in the current revision. Duplicate child targets, unknown segment ids, entries outside their segment ranges, and array entries that resolve to more than one target fail with `semantic_conflict` at the narrowest array field. Request-array order is discarded and the normalized collection ordering from Section 3 is receipt-bearing.

Unsupported command-specific fields fail with `unsupported_field`, `field=<field>` before target-version or recurrence-revision freshness checks. Stale item version fails with `stale_version`, `field=target_version`; stale recurrence revision fails with `stale_version`, `field=recurrence_revision_id`. If both are stale, `target_version` is reported first.

`occurrence_provenance.regenerate` requires `regenerated_at_utc`, `consumer`, `range_start`, and `range_end`; optional fields are `producer`, `range_basis`, and `occurrence_keys`. `range_basis`, `range_start`, and `range_end` use the Section 6 closed enum, defaulting, canonical endpoint formats, inclusive/exclusive predicate, and deterministic failure rules. When present, `occurrence_keys` MUST be a non-empty array; `[]` fails with `invalid_request`, `field=occurrence_keys`. `replace_stale_only` is not part of the MVP command surface and fails with `unsupported_field`, `field=replace_stale_only`.

Regeneration is atomic. It checks stale target version before stale recurrence revision. Selection first expands the canonical bounded range under Section 6, then intersects with `occurrence_keys` when present. Each supplied `occurrence_keys` element MUST be unique and MUST identify an occurrence selected by the canonical range predicate; duplicates or keys outside the selected range fail before writing with `semantic_conflict`, `field=occurrence_keys`. For every selected occurrence, Spine derives the provenance slot key, content hash, and provenance id before writing. Equal active slot plus equal content hash retains the existing row. A selected slot with different content supersedes the prior active row and writes the new active row. A selected slot with no prior active row writes the new active row. When `occurrence_keys` is omitted, any active provenance slot for the same consumer, item, recurrence set, and canonical range whose original scheduled fact is no longer selected is superseded without replacement. When `occurrence_keys` is present, slots not named by the request are outside the operation and are retained. All insertions, replacements, and selected-range removals occur in one transaction.

A successful `occurrence_provenance.regenerate` response returns `ok=true`, `command=occurrence_provenance.regenerate`, `command_receipt_id`, `item_id`, `item_type`, `target_version`, `current_version`, source item and shell lifecycle freshness facts, `recurrence_set_id`, `recurrence_revision_id`, `revision_number`, `normalized_recurrence_set_hash`, recurrence-set identity preimage facts, `changed`, `effect`, `consumer`, optional `producer`, canonical `range_basis`, canonical `range_start`, canonical `range_end`, `selected_count` as a decimal string, `selected_occurrence_keys`, `retained_occurrence_provenance_ids`, `newly_active_occurrence_provenance_ids`, `superseded_occurrence_provenance_ids`, `closed_block_report_ids`, and `unresolved_block_reports`. `selected_occurrence_keys` is always present as the deterministic ordered array selected by the canonical range and optional request intersection; it is empty when `selected_count="0"`. `closed_block_report_ids` contains every report atomically changed to `resolved` or `superseded` by the command, ordered by report id. `unresolved_block_reports` is always present and is an array; it is empty when all matching open reports are closed, and otherwise each element contains `block_report_id`, `reason_code`, and the report range/hash facts that prevented resolution.

The terminal `effect` enum for `occurrence_provenance.regenerate` is closed and receipt-bearing. Compatible same-command replay returns the stored `changed` boolean and stored `effect` string byte-for-byte. Fresh execution chooses exactly one effect after provenance selection and report resolution in this precedence order: `provenance_regenerate_replaced` with `changed=true` when any active provenance row is written or any prior active row is superseded; `provenance_regenerate_resolved_report` with `changed=true` when provenance rows are unchanged but one or more matching canonical or unresolved-range reports are resolved or superseded; `provenance_regenerate_unresolved_report` with `changed=false` when provenance rows are unchanged, no report is closed, and unresolved matching reports remain; `provenance_regenerate_zero_selected` with `changed=false` when selection is empty, no active row requires supersession, and no unresolved matching report remains; and `provenance_regenerate_all_retained` with `changed=false` when selection is non-empty, every selected occurrence retains an equal active provenance row, and no matching report remains unresolved or newly closed. The response arrays are authoritative supporting facts for each effect: zero-selected uses empty selected, retained, newly active, superseded, and closed arrays; all-retained populates selected and retained ids and has no new or superseded provenance ids; replaced reports every newly active and superseded provenance id, including fresh slots and selected-range removals; resolved-report populates `closed_block_report_ids`; unresolved-report populates `unresolved_block_reports`. The same effect strings MUST be used byte-for-byte in command receipts, replay comparison facts, conformance vectors, and operator reporting.

## 9. Implementation Slices and Failures

This contract is the only recurrence contract. Slice boundaries are delivery planning facts and MUST NOT be persisted in recurrence sets, hashes, cursors, receipts, provenance, or reports. Implementing daily local recurrence first does not create a second model or alter the meaning of any canonical field.

A partial runtime MUST fail an unimplemented command with `unsupported_command`, `field=command` before request-specific validation. Within an implemented command, an unimplemented canonical field fails with `unsupported_field`, `field=<first unsupported field>` after top-level shape validation and before stale checks or mutation. Validation scans present canonical fields in this order: `time_basis`, `frequency`, selector fields in lexicographic field order, `rdates`, `exdates`, `overrides`, `segments`, `range_basis`, `edit_scope`, response field request, and diagnostics. A runtime MUST NOT persist lossy approximations, silently discard fields, or report contract conformance while any required canonical vector is unsupported.

Failures that depend on current recurrence truth include `recurrence_set_id`, `recurrence_revision_id`, `normalized_recurrence_set_hash`, recurrence-set identity preimage facts, and the first unsupported field. Cursor, receipt, provenance, and block reports include the contract and normalization versions plus recurrence-set identity preimage facts so retries can distinguish stale truth, immutable-identity conflicts, and malformed requests.

## 10. Downstream Provenance and Side-Effect Boundary

Virtual occurrences are not persisted work. Before reminders, work instances, projections, relations, adapter requests, or side effects bind to an occurrence, the downstream record or dedicated `occurrence_provenance` row MUST persist producer, consumer, item/source/shell freshness facts, recurrence snapshot facts, occurrence id/key and provenance slot key, bounded range, original and expressed scheduled facts, timezone facts, source id arrays, source entries, optional override id, lifecycle, actionability, contract, normalization, and canonical-JSON versions, normalized recurrence-set hash, and recurrence-set identity preimage facts.

`occurrence_provenance` rows are immutable semantic snapshots with a one-way management envelope. The envelope field is exactly `management_status`, whose closed values are `active` and `superseded`. An active row MUST omit `superseded_by_command_id`, `superseded_at_utc`, and `replacement_occurrence_provenance_id`. Superseding a row atomically changes only its management envelope: it sets `management_status=superseded`, records the regenerating `superseded_by_command_id` and its canonical action timestamp as `superseded_at_utc`, and records `replacement_occurrence_provenance_id` when a selected slot receives a new active snapshot. The replacement field is absent when a full-range regeneration removes a disappeared slot without replacement. A superseded row can never return to active and no semantic snapshot field may change during supersession.

Active-row uniqueness is the generated `occurrence_provenance_slot_key`, whose preimage is registered in Section 5. It deliberately excludes `recurrence_revision_id` and `occurrence_key`: a later revision for the same original scheduled slot replaces the active semantic snapshot instead of leaving a stale active row under a dead revision key. The slot's `range_basis`, `range_start`, and `range_end` are the Section 6 canonicalized range facts after defaulting and endpoint validation. Implementations MUST NOT store omitted `range_basis`, noncanonical endpoint strings, or basis-specific coercions in occurrence provenance rows. Equal active slot plus equal content hash is compatible semantic replay and retains the existing row without changing its management envelope. Equal active slot plus different content hash requires atomic replacement and supersession with linkage from the old row to the new row. A selected slot with no predecessor is inserted as active, and a prior active slot no longer present in a full-range selection is superseded without replacement. Superseded rows remain replay facts and MUST NOT authorize downstream action.

External writes MUST persist a `side_effect_attempts` row before invoking an adapter. The ontology owns the generic attempt ledger; recurrence MUST NOT create a second attempt lifecycle. Recurrence-bound attempts link persisted occurrence provenance through work, candidate-action, or projection origin. If provenance is stale by item version, shell lifecycle facts, contract version, normalization version, recurrence revision, normalized recurrence-set hash, recurrence-set identity preimage facts, or Section 3.1 hash preimage content, downstream work, projection writes, reminder sends, and side-effect starts fail closed before adapter invocation until replacement provenance is produced. A downstream consumer MUST NOT treat a changed `time_basis` or timezone fact under the same `recurrence_set_id` as refreshable staleness; that condition is an immutable-identity conflict and fails with `semantic_conflict`, `field=recurrence_set_id`.

Read-only inspection commands persist nothing. Section 8 or an explicitly configured worker regeneration path is the only producer of replacement occurrence provenance. Stale provenance preflight blocks persist `report_version=spine.recurrence.provenance-block.v1` with item, consumer, operation, canonical range facts, stale/current facts, occurrence facts when known, `reason_code=stale_occurrence_provenance`, and `handoff=occurrence_provenance.regenerate`.

A provenance-block report is a durable Spine report artifact produced by the recurrence preflight guard, not a side-effect attempt and not a second adapter-result ledger. Its producer is `spine.recurrence.preflight`. The persisted report payload contains `report_version`, `item_id`, `consumer`, `operation`, `recurrence_set_id`, canonical `range_basis`, canonical `range_start`, canonical `range_end`, stale `occurrence_provenance_id` when known, current `source_item_version`, current `contract_version`, current `normalization_version`, current `canonical_json_version`, current `recurrence_revision_id`, current `normalized_recurrence_set_hash`, current recurrence-set identity preimage facts, optional `occurrence_provenance_slot_key`, optional snapshot-only `occurrence_key`, `reason_code=stale_occurrence_provenance`, `handoff=occurrence_provenance.regenerate`, `status`, decimal-string `block_count`, `first_blocked_at_utc`, `last_blocked_at_utc`, and latest stale/current fact snapshot. The deterministic `block_report_id` uses prefix `recurrence_provenance_block` over Spine canonical JSON containing exactly `derivation_version=spine.recurrence-provenance-block-id.v1`, `report_version`, `item_id`, `consumer`, `operation`, `recurrence_set_id`, canonical `range_basis`, canonical `range_start`, canonical `range_end`, stale `occurrence_provenance_id` when known, current `source_item_version`, current `contract_version`, current `normalization_version`, current `canonical_json_version`, current `recurrence_revision_id`, current `normalized_recurrence_set_hash`, current recurrence-set identity preimage facts, and optional `occurrence_provenance_slot_key`; absent optional facts are omitted. Snapshot-only `occurrence_key` is not an identity or open-uniqueness fact because a changed recurrence selector may produce a successor key for the same slot. Open-report uniqueness is the same field set as the id preimage. Repeated preflight blocks with the same open-report uniqueness key update that report's `last_blocked_at_utc`, decimal-string `block_count`, and latest stale/current fact snapshot; a different key appends a new open report. Legal canonical report statuses are `open` and `resolved`. Resolved canonical reports are immutable audit facts and never reopen. A later preflight block with the same deterministic key as a resolved canonical report MUST fail closed with `semantic_conflict`, `field=block_report_id`, returns a structured failure envelope, and does not update the resolved report, create a successor report, invoke an adapter, or start a side-effect attempt. Successful `occurrence_provenance.regenerate` resolves every open `spine.recurrence.provenance-block.v1` report for the same consumer, item, recurrence set, canonical range facts, and provenance slot when present when the resulting active provenance satisfies the regenerate command's current freshness facts. The report's stored version, revision, hash, and occurrence-key snapshots are historical observations and need not equal the later command truth; resolution records both snapshots, `resolved_by_command_id`, `resolved_at_utc`, and resulting `occurrence_provenance_id` values.

If the preflight guard cannot determine canonical range facts, it MUST NOT use `spine.recurrence.provenance-block.v1` or the `recurrence_provenance_block` identity path. Instead it persists or updates `report_version=spine.recurrence.provenance-block.unresolved-range.v1` with `reason_code=provenance_range_unresolved`, `item_id`, `consumer`, `operation`, `recurrence_set_id`, current `source_item_version`, current `contract_version`, current `normalization_version`, current `canonical_json_version`, current `recurrence_revision_id`, current `normalized_recurrence_set_hash`, current recurrence-set identity preimage facts, optional stale `occurrence_provenance_id`, no `range_basis`, `range_start`, `range_end`, or `occurrence_key`, `handoff=derive_canonical_range_then_occurrence_provenance.regenerate`, `status`, decimal-string `block_count`, `first_blocked_at_utc`, `last_blocked_at_utc`, and the latest known stale/current fact snapshot. The deterministic unresolved-range `block_report_id` uses prefix `recurrence_provenance_block_unresolved_range` over Spine canonical JSON containing exactly `derivation_version=spine.recurrence-provenance-block-unresolved-range-id.v1`, `report_version`, `item_id`, `consumer`, `operation`, `recurrence_set_id`, current `source_item_version`, current `contract_version`, current `normalization_version`, current `canonical_json_version`, current `recurrence_revision_id`, current `normalized_recurrence_set_hash`, current recurrence-set identity preimage facts, and optional stale `occurrence_provenance_id`; absent optional facts are omitted. Open-report uniqueness is exactly that preimage field set. Repeated unresolved-range blocks with the same open key update `last_blocked_at_utc`, increment `block_count`, and replace only the latest fact snapshot; a different key appends a new open report.

Unresolved-range report statuses are `open`, `superseded`, and `resolved`. A later preflight, a configured range-derivation worker, or `occurrence_provenance.regenerate` with explicit canonical range facts may close an open unresolved-range report atomically. The closer selects open reports by item, consumer, and recurrence set and, when present, stale provenance id; it MUST NOT require historical report version, revision, or hash snapshots to equal later command truth. Regenerate records its canonical request range as the derived range and proves freshness against its own current command facts. When stale provenance still blocks, the closer creates or updates the canonical range-bearing report, sets the unresolved report to `superseded`, and records both freshness snapshots, `closed_at_utc`, `closure_kind=canonical_range_derived`, and `successor_block_report_id`. When regeneration or derived-range inspection proves that no stale provenance block remains, it sets the unresolved report to `resolved` and records both snapshots, `closed_at_utc`, and `closure_kind=canonical_range_derived_no_stale_provenance`. A closure attempt that refers to a different item, consumer, recurrence set, or supplied stale provenance id fails with `semantic_conflict`, `field=block_report_id`. No separately configured worker is required for recovery when an authorized regenerate request supplies a valid canonical range. Closed reports remain immutable audit facts and never reopen; a later block derives or updates the report identified by the then-current open-report key.

If the preflight guard cannot persist or update the required report atomically, the downstream operation remains blocked, no adapter invocation or side-effect attempt may start, and the caller receives a command-contract structured failure envelope with `ok=false`, `command` when known, `error.code=runtime_failure`, `error.field=provenance_block_report`, and `error.message` naming the atomic report persistence failure. A blocked caller response for the canonical report is also a structured failure envelope: it MUST include `ok=false`, `command` when known, `error.code=runtime_failure`, `error.field=occurrence_provenance`, `error.message`, plus `reason_code=stale_occurrence_provenance`, `block_report_id`, `report_version`, `handoff=occurrence_provenance.regenerate`, `consumer`, `operation`, canonical `range_basis`, canonical `range_start`, canonical `range_end`, current recurrence freshness facts including recurrence-set identity preimage facts, stale provenance facts when known, and occurrence facts when known. A blocked caller response for the unresolved-range report MUST include the same structured envelope fields with `error.code=runtime_failure`, `error.field=range`, and `error.message`, plus `reason_code=provenance_range_unresolved`, `block_report_id`, `report_version`, `handoff=derive_canonical_range_then_occurrence_provenance.regenerate`, `consumer`, `operation`, and current recurrence freshness facts known to the guard.

## 11. Conformance Vectors

Conformance vectors MUST publish canonical JSON inputs, normalized recurrence-set hash preimages, generated-id preimages, expected digests, expected ordered occurrences, expected cursor payloads, expected receipts, expected failures, expected diagnostics, and expected provenance-block reports. A vector that asserts only returned occurrence dates is not sufficient for this contract.

Required MVP vector families are:

- `canonical-json-and-normalization`: canonical JSON escaping, Unicode, explicit-null patch values, absent optionals, numeric-string rejection, normalized child ordering, normalized `segment_ref`, and full preimages plus digests.
- `authoring-time-bases`: `spine.recurrence-authoring.v1` creation for `local_date`, `local_instant`, and `instant_utc`, including generated empty collections and immutable recurrence-set identity facts.
- `persistence-authority`: atomic initial authoring and changed recurrence mutation bundles for events and tasks, immutable prior rows, recurrence-bearing anchor references, contiguous item versions, recurrence revision ownership, audit and receipt co-commit, and rollback on every injected failure point.
- `daily-weekly-selectors`: daily interval expansion, every-three-days expansion, weekly `week_start=MO` default, non-default week starts, weekly interval alignment, and seed-weekday default.
- `monthly-yearly-selectors`: positive and negative month days, invalid-date omission, `by_set_position` for monthly and yearly rules, seed-derived month/day defaults, and selector-combination rejection.

## 12. Acceptance Criteria

1. **AC-01 — Canonical bytes.** Two conforming implementations produce byte-identical normalized payloads, hashes, ids, cursor digests, receipt hashes, and report ids for `canonical-json-and-normalization`.
2. **AC-02 — Flexible schedules.** Both implementations produce the same ordered original occurrences for `daily-weekly-selectors`, `monthly-yearly-selectors`, and `end-conditions-and-splits`, including every-three-days recurrence.
3. **AC-03 — Time bases.** Both implementations produce the same scheduled facts and timezone resolutions for `authoring-time-bases` and `time-resolution`.
4. **AC-04 — Source identity.** Both implementations produce the same occurrence keys, source unions, current source evidence, and carry-forward lineage for `source-union-and-rdates` and `target-carry-forward`.
5. **AC-05 — Bounded reads.** Both implementations accept and reject the same ranges and limits and produce byte-identical ordering, diagnostics, `has_more`, and cursor payloads for `bounded-pagination`.
6. **AC-06 — Lifecycle.** Every `overrides-and-actionability` case yields the specified effective detail state and exact JSON `actionable` value; no overlay reopens archived or terminal base truth.
7. **AC-07 — Mutation contract.** Every fresh, no-op, dry-run, and replay case in `mutation-effects` and `patch-replacement` returns the registered `changed`/`effect` pair and byte-identical receipt comparison facts.
8. **AC-08 — Set identity.** Every case in `immutable-set-identity` rejects in-place changes to recurrence-set identity facts before persistence and never silently creates a replacement set.
9. **AC-09 — Provenance refresh.** `provenance-revision-refresh` leaves at most one active row per provenance slot, retains equal content, replaces changed content, inserts new slots, and supersedes removed full-range slots atomically.
10. **AC-10 — Report recovery.** Every `provenance-effects-and-reports` case returns the registered terminal effect and can recover an unresolved-range block through an explicit valid regenerate range without requiring a configured worker.
11. **AC-11 — Side-effect boundary.** A stale or conflicting provenance case persists the required block report and prevents adapter invocation and `side_effect_attempts` creation until valid active provenance exists.
12. **AC-12 — Thin-slice honesty.** Every `partial-runtime-fail-closed` case rejects unsupported behavior deterministically without persisting a lossy approximation or a second recurrence model.
13. **AC-13 — Full agreement.** Across all Section 11 families, two conforming implementations produce the same identities, scheduled and expressed times, timezone resolutions, diagnostics, errors, receipts, lineage, provenance snapshots, block reports, and replay outcomes.
14. **AC-14 — Persistence authority.** Every `persistence-authority` case writes the complete item-version and recurrence-revision bundle atomically, preserves all prior semantic rows, and leaves no partial canonical truth after failure.
